# The patching harness

Patching is proven on the real thing, not on its own tests: a real scan, real pull requests, the real gate and merge queue, a real deploy and the next scan. That happens on two public scratch copies, `the-roganator/cv-software-factory-scratch` and `the-roganator/cv-worlds-worst-website-scratch`, and a k3d cluster of their own, `software-factory-scratch`, which the copies' `main` deploys. [`TESTS.md`](TESTS.md) is what must pass: it is Martin's, and changes only with him. A change to patching is tried here, by the tests it touches and then the whole pass, before its pull request opens.

## Never

- **Never the real cluster.** Every command names the context `k3d-software-factory-scratch`; never `k3d-software-factory`. Never run `make` for the scratch cluster from a checkout of this repository: only in the factory copy's clone, `work/factory` in the state folder, whose Makefile names the scratch cluster, as `bin/copies.sh` does (it refuses a clone that names the real one).
- **Never `make upgrade-cluster` in the copy.** The copy pins an older k3s and k3d on purpose, for test 14, and it would move the scratch cluster down to them.
- **Never write to the real repositories.** The scripts write only to a repository whose name ends `-scratch`, and refuse any other; the real two are read, to build a baseline and to close what they closed.
- **One session at a time.** A run resets the copies and restarts the scratch cluster's workers; two at once read each other's pull requests as their own. Before starting, `pgrep -fl 'confirm.sh|harness.ts|copies.sh'` prints nothing, and no `batch.env` or file in the state folder's `staged/` was written minutes ago: either is another session's.
- **Look at the shared runners before a reset.** The copies queue on the organisation's free runners beside the real repositories: `gh run list -R the-roganator/cv-software-factory --status queued` prints the real repository's queued runs, and nothing when none waits. A run in progress does not count. A reset or a batch starts a dozen runs; when the real ones are waiting, wait.
- **Never `kubectl delete job migrate`** on the scratch cluster: its Argo CD finalizer hangs the delete and every sync behind it.

A pass's timings are part of its verdict: keep the Mac quiet while one runs.

The skill's files are tracked; what a run makes and keeps is in the **state folder**, the main checkout's git-ignored `scratch/patching-harness/` (`PATCHING_HARNESS_STATE` names another), found the same way from any worktree.

## The copies and the scratch cluster

`./copies.sh status` says where each copy's `main` and `baseline` are and what is open; `kubectl --context k3d-software-factory-scratch -n argocd get app root` says whether the cluster is Synced and Healthy; its console is `https://console.localhost:9443` (a browser keeps one sign-in per host, so signing in there signs you out of the real console). The copies are ready when `status` shows each copy's `main` at its `baseline` and root is Synced and Healthy. `main` ahead of `baseline`, with a few pull requests open, is the copies after a run (its deploy pins and moves merged on top), which a reset puts back.

From nothing, once: `./copies.sh build`, `check`, then the once-only `create` (the repositories, their settings, keys and variables) and `up` (the cluster, by the factory copy's own `make up`, with the scratch App's key from the Keychain; `./copies.sh app` makes a new App, which Martin creates and installs on the two copies alone, and writes `app.env`). Then Martin enrols his passkey (`make enrol` in `work/factory`) and sets the controls in its console (Guarded, auto-merge on, new work on), and `./copies.sh store-save`, once, keeps that store as the clean point every reset can go back to. Then a baseline (below).

A copy is the real repository at the baseline's commit with the vulnerable pins put back, every real name renamed to the copy's (`rename.pl`), the cluster's names, ports and App made the scratch cluster's (`cluster.pl`), and what the renames invalidate made again (formatting, samples, the scan's recorded answer, the refusal records' hashes, `rehash.ts`). The app calls the factory copy's workflows at the factory baseline, so every gate a copy's pull request meets is the copy's code. The factory copy carries a version tag (`DEPENDABOT_TAG`), which every push of its baseline puts back, so the app copy's Dependabot follows its `main` for the workflows it calls (test 20). The copies have the real ones' rulesets, environments and labels, from the baseline's own `scripts/github-settings.ts` (`./copies.sh settings`).

## A baseline

A baseline is a real commit of each repository (`FACTORY_FROM`, `APP_FROM`), the merged moves reverted so their pins are vulnerable again (`*_REVERTS`), and the patches in `staged/`, each a commit, applied after the reverts and before the rename. Two kinds of patch are not those. `STAGED_EXTRA` in `batch.env` names a test's own folder beside this file (`staged/factory-x2/`, `staged/app-x4/`), applied after the rest, for that test's baseline alone. A local patch is any file in the state folder's `staged/<side>/`, applied with the committed ones whatever the baseline, and kept by no commit. Look in the state folder's `staged/` before building: what is there goes into the baseline.

Every baseline is these four steps, and the cluster after them:

```sh
./copies.sh build       # about 4 minutes; ends "== built: factory …, app …"
./copies.sh check       # about 2
./copies.sh reset       # about 5
./copies.sh pin-images  # about 9; ends "== pinned: factory …, app …"
kubectl --context k3d-software-factory-scratch -n argocd get app root \
  -o jsonpath='{.status.sync.revision} {.status.sync.status} {.status.health.status}'
```

`build` prints each patch it applies, marking a local one, and names the local ones again in its last line. Its many "Automatic merge went well" lines and a warning about CRLF are the reverts, and are noise. `check` is `make check` in both clones. `pin-images` builds each copy's images on its `main` and pins their digests in a commit on top. That commit is the baseline: its `pinned:` pair supersedes `build`'s `built:` pair. The cluster is on it once root's revision is the `pinned:` factory commit, Synced and Healthy, about seven minutes after `pin-images`. Suspended for a few minutes on the way is the app's canary pausing, which clears unaided. A set-up patch is written against the real repository at `FACTORY_FROM` or `APP_FROM` with the reverts applied, naming the real repositories, with `# <why>` as its first line; each must still pass `make check` (the inventory's `--unlisted`, a frozen install, the scan's recorded answer), and must leave the app's `package.json` naming the registry's ranges alone (no alias, tarball, folder or git source), or the pin step refuses every lockfile move.

## Reset

`./copies.sh reset [factory|app] [--store]` puts a copy back to its baseline and closes everything open; `--store` also restores the scratch store (`store-restore`, which then runs the baseline's migrations). A run resets for itself. After a reset the scratch worker starts opening the baseline's moves at once: with the pin watch on every move, a dozen pull requests. When no run follows, `./copies.sh worker 0` stops it. A reset closes pull requests as Martin's login and then retitles them `chore(reset): …` and clears their marks (`forget-closed`), so the watches open them again. It keeps the Dependabot pull requests the tests need (`DEPENDABOT_KEEP_*`), whatever the real repository did with its own, and opens again any of them that is closed (the newest closed one of each alternative of the regex), then asks Dependabot to make it again on `main` (`@dependabot recreate`), as the branch it reopens stands on a `main` from before the baseline, and summons Dependabot on that copy once (`./copies.sh summon-dependabot factory|app`, one commit on its `main`) while one it reopened still conflicts or is older than the baseline's push; it closes the rest, and any the real repository closed. One kept as it is (`DEPENDABOT_AS_IS_FACTORY`: Playwright's on the factory copy, which test 22's worker must leave alone) is only opened again: Dependabot answers nothing asked of that one, and it is no reason to summon. A run whose test is judged on a pull request of Dependabot's (N1, 22) looks for it before its clock starts, open, its head made since `main` was last put at the baseline and not conflicting (one kept as it is, open); without one it opens it once more (`./copies.sh reopen-dependabot factory|app`), waits five minutes at most, and stops with "pre-flight, no verdict" without it.

## Running tests

Set the level first: `./level.sh guarded` (the default for every test), `supervised` or `lights-out`; the worker reads it within a minute.

- **One factory test, or a few:** `node harness.ts factory --only 1,2` (75 minutes at most): it resets the factory copy, scans, forges (name `N3a,N3b,N4,N5` to run the forgeries, or add `--no-forge`), restarts the worker, watches, and scans again. The watch looks every 20 seconds and says where each test stands when that changes. It ends once every test is decided (a move merged and deployed; a refusal, forgery or held major unmerged and unqueued with its checks and the gate's verdict in, and, but for a forgery, its checks green and the worker's word that it waits for the level or the verdict; a test whose failure nothing can undo, which the log names as "has failed, whatever comes"), and otherwise at the limit (`--limit`, 60 minutes); W1b watches until its head has been out of runs for nine of the worker's passes, 100 minutes at most. `--lights-out` expects the majors (4a, 4b) merged; without it they must be held.
- **One app test:** `node harness.ts app 13` (about 40 minutes, W3 an hour). It resets the app copy, restores the store, promotes the app's release of its baseline whole and waits for it to be Healthy, and tells the line which ticket to take. `--with X1a,X1b` carries the app's forgeries beside it, and `--with 24` the move nobody can make, an issue of the worker's from the same scan: the run tells the pin watch that one move by name before it restarts the worker, as the worker's pass over the app's repository opens an issue only for a move the watch was told, and an issue rolls nothing (`app 24 --no-reset --no-scan` reads it alone from the app copy's latest scan, in about seven minutes, with no ticket taken); `app X1a --with X1b` runs them alone. One at a time: each needs the line to itself. An app test is judged clean on one look at every pod, so the factory copy must rest under it: the pre-flight refuses the run while the App has a pin move open there, or a deploy pin on a `main` past the baseline, either of which would merge and roll the factory. `node harness.ts rests` says whether it rests; `node harness.ts batch none`, then `./copies.sh reset factory` and root Synced and Healthy, puts it at rest, the pin watch taking no move. `app W5` resets nothing and scans nothing: it leaves a report through the app's widget, keeps the store's pod away for some 25 seconds (deleting it again as the StatefulSet puts it back), so two of the log watcher's ten-second turns fall inside, and reads the inbox and every worker's log. It passes only when the watcher's own log has its warning that a check could not reach the store and then its word that it reached it again, with the report in the inbox once and no error from any worker; with no such warning it reads "no verdict: the restart fell between the watcher's turns" (about five minutes; the report becomes a ticket in the scratch store, which the next app test's restore takes away). Test 20 is Dependabot's pull request, which the line has no part in: `app 20 --with N8a` resets the app copy, forges, summons Dependabot and watches the worker queue its pull request.
- **A batch** is a few factory tests on the baseline as built, with the pin watch taking only their moves: `node harness.ts batch 1,2,5` writes their `PIN_WATCH_ONLY=…` line to the state folder's `batch.env` in place of any there, and reads it back as `copies.sh` will before it says what the watch takes (`only 1,2,5` prints the line and writes nothing); then `factory --only 1,2,5`. Its reset of the factory copy writes the line to the ConfigMap `scratch-pin-watch`, from which the scratch worker reads it as it starts (no commit holds it, and Argo CD does not track it), and the pre-flight refuses a run whose tests' moves it leaves out. `batch.env` stays until it is changed. With no `PIN_WATCH_ONLY` line in it, a reset writes `*`, and the worker takes every move; with the line `batch none` writes, which names nothing, or no ConfigMap at all (a cluster no reset has touched), it takes none. Tests 6, 7a, 7b and 9 share one pull request, so name them together.
- **The whole pass:** `./confirm.sh <a folder for its logs>`: one baseline, then batches A (1, 2, 3, 5, 14a, 17, N6 and the forgeries, N7 among them, with 22 beside 1), B (4a, 4b, 6, 7a, 7b, 9, 14b, 15, 18, and beside them 23, which takes no time of its own), C (the majors at Lights-out, 18 among them, with N6 and N7 again), each of the three judging 19 too, D (Supervised queues nothing but the deploy pin; it watches until the deploy pin has merged and each move's pull request has its checks in and the worker's word on why it waits, 35 minutes at most; it ends by putting the factory copy at rest before the level goes back to Guarded), the eight app tests with 24 beside 8a, the forgeries X1a and X1b beside 13 and N8a beside 20, and W (W5, W2, W3, W3b and W4 with the factory copy at rest, then W1). `STEPS="C D"` runs some; `STEPS=X`, `STEPS=X4` and `STEPS=21` run X2, X4 and 21, each on a baseline of its own.

The recovery tests W1 and W2 turn a check red on purpose, by repository variables the factory copy's title check reads (`staged/factory/15-…`). `node harness.ts variables W1a,W1b` prints them; `confirm.sh` sets them for the run and clears them on any exit, and the harness refuses a run while one is set that its tests do not need. W1 is a batch of its own (`only W1a,W1b`), never beside test 2 or 3. X2 needs `STAGED_EXTRA=x2` in `batch.env`, and X4 `STAGED_EXTRA=x4` and no `check` (the app's own Node pin test refuses its half-made state by design); take the line out after, or every later baseline carries it, which the harness refuses. 21 needs `STAGED_EXTRA=21`, which adds a patch to each side. X3 is not staged: no real pin separates the publisher's Critical from Trivy's, so unit tests prove it.

## Reading a verdict

`node harness.ts summary` prints one line a test from its latest finished run; `report <run>` a run's lines; `resume <run>` carries on a stopped one; `reread <run>` judges a finished run again from what it recorded, reading nothing from the copy or the cluster, which a later reset has emptied; `reread <run> --scan2 <id>` first reads that scan's `moves.json` as the run's confirming scan, for one that finished after the run stopped waiting.

Believe a verdict only once GitHub and the cluster say the same. A run checks what it stands on before its clock starts (the store at the baseline's newest migration, the app's release of its baseline whole, its staged extras those its tests ask for) and stops with "pre-flight, no verdict" on a set-up fault: mend the set-up and run again. A surprising PASS or FAIL is checked against the pull request, its checks and the worker's log in `runs/<run>/logs/` before anything is changed for it: a verdict is the harness's reading, and the harness can misread as surely as the code can fail.

## Taking a newer main

1. Set `FACTORY_FROM` and `APP_FROM` in `baseline.env` to the new commits. `./copies.sh build` says which revert or staged patch no longer applies: a revert whose move `main` reverted itself goes, and a patch is written again against the new commit.
2. Check each test still starts from a vulnerable pin: `catalogue.ts` names each test's pins. A move `main` has merged since needs its merge added to `*_REVERTS`.
3. `check`, `reset`, `pin-images`, then `./copies.sh settings`: the copies' rulesets and disabled workflows follow the baseline's code. A migration `main` renumbered needs the scratch store's `schema_migrations` row renumbered too.
4. The whole pass.

## Traps

- **A run that summons Dependabot for test 22 leaves `main` one commit past the baseline.** The commit is pushed at the end of the reset, before the worker starts, so it is the reset's push: the run stands on that push's scan and its clock starts there, and the baseline's own push's scan, a minute older and of the same pins, may be replaced by it. The factory copy then does not rest for an app's test until its next reset. A run that finds Dependabot's pull request open pushes nothing.
- **Dependabot's pull request for Postgres cannot be had on demand, and each pass of test 22 spends one.** Seen on the factory copy on 25 November 2026 (UTC): a summon at 21:48 brought #892 within two minutes, though a reset had closed #759 the day before; the baseline's own push brought #894 at 22:12:57; a reset closed #894 by hand at 22:25:11, and the summon at 22:25:44 (Dependabot's run began at 22:25:49) and another run at 22:31:53 opened none. It is not known why those two runs opened none: that Dependabot skips a version whose pull request was closed by hand is the likeliest reading, and #759 and #892 speak against it. `@dependabot reopen` on #894 had no answer, and its branch was gone. So a reset no longer closes it, and a run takes whichever is open. Once the worker closes one as a duplicate, which is the test's pass, the next run needs another: it summons, waits ten minutes, and drops test 22 with no verdict if none comes. Dependabot's own daily and weekly runs, or a new baseline's push, may bring one before then.
- **The clock starts at the scan the pull requests come from.** A reset that pushes the baseline to `main` starts a scan, which the worker opens its pull requests from: the run records the reset's commit and time, stands on that push's scan, and starts its clock there. The limit runs from it too, so the pre-flight's minutes (the app's release, the store) come out of a test's hour, as they come out of the worker's: its pull requests are open while the pre-flight waits. A reset that finds `main` at the baseline already pushes nothing, and the run dispatches a scan of its own, after code scanning has an analysis of `main`; pull requests the worker opened from an earlier scan of the same commit are then older than the clock. The run's log says which scan it took, and why.
- **A scan can fail on a registry's rate limit** and leave no moves. Run again with `--no-reset`, with `resetAt` in the run's `state.json` set to the reset's time, or pull requests opened before the new scan are missed. A scan's conclusion reads `failure` whenever it has findings: that is not this.
- **A `platform` run can hang** on the Argo CD install's image pull and end at the step's or job's limit; the merge queue's and the worker's recoveries then run it again. The failed job's step `Why: …` carries the runner's figures: `gh api repos/<copy>/actions/runs/<run>/jobs --jq '.jobs[].steps[].name'`.
- **The first deploy pull request after a reset is red by design** (`lint, types, tests`): its base reached `main` by a force-push, not the merge queue. The worker runs its checks again twice and says it is out of runs, about a quarter of an hour after every factory reset; that is no fault.
- **A ticket restored with the store is days old.** The scan's send for it appends no event when it says what the ticket already holds, so the harness reads the inbox for the work item triage counted the send on, takes that ticket, and times "stuck" from the take. With no row in four minutes it takes the open ticket as it stands.
- **A routine update shares a lockfile's name.** `moves.json` names every lockfile move "a package in …", routine or not, so the harness tells them apart by what they clear and by the pull request's branch (`…-routine-<8 hex>`), never by name.
- **A reset restarts an image's or a chart's routine wait.** The scan counts a routine update's three days from the day it first saw the release, kept in its state, for an image or a chart, and a reset deletes the state; a package's it counts from npm's publish time. So a routine test stands on a package.
- **The scan that confirms a run is not always the one the run dispatched.** The scan's job keeps one pending run, so a push of `main` while a dispatched scan waits replaces it, and GitHub cancels it. The run takes the newest finished scan of `main` on a commit that holds every merged test's merge commit, waits for one queued or running on such a commit, and dispatches only when there is none; a cancelled scan is no test's failure. It reads that scan's `moves.json` before it ends, and the pass's next reset comes only after: a reset deletes nothing a finished scan's artifact needs, but a scan still running through one loses the alerts and the state it reads.
- **`*` in the pre-flight's line means every move.** A small run whose ConfigMap says `*` opens every pull request of the day, and at Lights-out merges them all; the pre-flight says so in words. `node harness.ts batch <tests>` is what names the batch's moves, and it fails if `batch.env` does not read back as it wrote it.
- **Every factory scan ends red, by design.** The baseline pins an image no registry serves (test 19), so each scan's run has an "Image not read" annotation and fails at its end with everything uploaded. A scan that left no `moves.json` is the fault, not the red.
- **The pin watch takes every move of a name.** Test 18's move is named "a package in `pnpm-lock.yaml`", as every development dependency's is, so in B and C the watch also opens the day's routine updates of the others (one pull request, on the `-routine-` branch), which merge unjudged.
- **Once a pull request has merged the harness asks Argo CD to look at git,** twice a minute until the move is deployed: a refresh, which hastens Argo CD's own poll of two to three minutes and changes nothing in the cluster.
- **The App may not write a workflow file, and that is N7.** The scratch App has no `workflows` permission, as the real one has none, so GitHub refuses its commit of a workflow file: N7 passes on that refusal, quoted in its line, and only if the push lands is its pull request judged by the gate. Nobody but Martin and Dependabot can put a workflow change on a branch of a copy, and a pull request Martin opens passes the gate by rule, so the forge never opens one as him.
- **N8 shows one hold live.** N8a's branch is pushed as Martin's login and its pull request opened by the scratch App; the gate holds it as the App's own change to a code-owned path (`Held for its risk tags (code-owned)`): it is no exact pin of the factory's workflows, since Dependabot did not open it, which the gate asks before it reads the commit the calls moved to. So N8b and N8c (a commit not on the factory's `main`, a commit behind the pinned one) and N8a's third-party line are proven by the gate's unit tests alone (`scripts/review-routing.test.ts`, "an exact pin of the factory's workflows"): nobody can open a pull request as Dependabot.
- **A worker that cannot read the scan ends the batch.** When the worker's log says "The scan's moves in … cannot be read" on three passes, every move of the batch that has no pull request has failed, and the watch says so with the line and ends, not at the hour.
- **Argo CD puts back what you take away** within seconds, Postgres among it. To keep the store away for a test, delete its pod repeatedly.
- **Postgres goes to 18.7 in test 1 and back to 18.6 at each reset;** `store-restore` strips what 18.6 refuses.
- **An ordinary work item on the app before a run** leaves a fix the next reset takes back, and the canary aborts that release. The pre-flight promotes the baseline's release whole.
- **The look at the cluster waits for a rollout in flight.** A deploy pin that merges as the watch ends rolls the factory's Deployments, and the probes' pod, with its long pull, is Ready only after its first pass: before its one look the run waits five minutes at most for pods that are starting, of a Deployment whose rollout is progressing, with no restart and no back-off. One not Ready after that is unhealthy, as any is.
- **N1 cannot be staged on the app copy since 19 November 2026, and test 12 runs with no pull request of Dependabot's beside it.** A pull request of Dependabot's for one dependency that is closed by hand is skipped by Dependabot from then on, and its branch is deleted: the app copy's #1 (Node, closed 19 November) and #266 (Syft, closed 22 November) cannot be reopened, and no summon makes them again. N1's subject is that pull request, so it reads NOT RUN, "pre-flight, no verdict", until Dependabot opens one for a later release. Test 12's subject is the line's own move: it runs, and its line says there was none beside it, or, where there is one, what became of it after the merge (closed by the App as a duplicate is the worker's duplicate watch in the app's repository). A reset must never close a kept one: `reset_one` closes no pull request of Dependabot's, and `dependabot_only_needed` and `dependabot_like_real` both pass over every title `DEPENDABOT_KEEP_*` matches.
- **Dependabot opens pull requests on the copies** at no set time, and a fresh push opens about ten at once: `DEPENDABOT_KEEP_*` keeps only those the tests need.
- **A hold is decided once.** The pin watch writes a held pull request's head again when `main` moves under it, and the worker says why a head waits once a head: the run records the first head a hold was decided at, and from then the test stays held unless it merges, is queued or touched, or the gate judges a later head by another rule.
- **The next scan may list the same pin again, from where the move left it.** A chart moved to one release is listed from that release to the next: a move of the first scan is still there only when the next scan has one of its name from the same version.
