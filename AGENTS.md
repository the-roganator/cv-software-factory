# AGENTS.md

Software Factory: AI agents and deterministic gates that look after a live web app, built by Martin Rogan as a portfolio demo.

Read [`docs/INTENT.md`](docs/INTENT.md) first: why this exists and the bar everything is held to. Then [`docs/AGENTS.md`](docs/AGENTS.md), which signposts the specification and other docs.

Everything you write here is public and part of the demo. Write for a thoughtful reviewer.

## Working here

```sh
mise install && pnpm install   # the toolchain mise.lock holds, dependencies and git hooks
make check                     # what CI requires: lint, types, tests, design tokens, manifests
pnpm dev                       # the console on :5173 with the samples, reloading on change
make e2e                       # every browser test CI runs, live ones too, in the pinned Playwright image
make zap                       # ZAP's baseline scan of the console signed in as Martin, as CI runs it
make up / make samples / make status / make down
make upgrade-cluster           # move the cluster to the k3s deploy/k3d/cluster.yaml pins, keeping everything in it
make enrol                     # a one-time code to enrol a passkey on the console
make share-key                 # the traffic generator's signing key, made once, and its public half for the app
make refusal-key               # the GitHub worker's key for signing its refusals, made once, and its public half for the line and the console
make judgements-token          # triage's token for the gateway's judgements, made once
make guardrails                # every guardrail's proof but the attacks, recorded in the store, from a clean main (PROOFS="…" for some); the drill asks first
```

The local cluster (its console at `https://console.localhost:8443`, its certificate, its state, `make upgrade-cluster`, signing in, Pushover, the scoreboard's key) is [`docs/LOCAL-CLUSTER.md`](docs/LOCAL-CLUSTER.md). Running a part of the factory on the host against it (each worker, the gateway, the admin service, the smoke run, the line's settings and `soak-check`, the bench, the flags) is [`docs/ON-THE-HOST.md`](docs/ON-THE-HOST.md).

- Node 24 runs TypeScript directly: erasable syntax only, `.ts` extensions in imports, no build step. The console's browser code is the exception: Vite builds it.
- In the console, anything that runs every frame (a drag, a wipe, the reel settling) writes to the DOM through refs, and component state changes only when the movement ends. A test counts renders during a drag.
- Visual snapshots are taken in the pinned Playwright image, never on the host: `make e2e` refreshes them with `UPDATE=1`.
- Commits and pull request titles are Conventional Commits (`scripts/commit-msg.ts` checks both). Pull requests are squash-merged; nothing is pushed to `main`.
- Pull requests that build on each other's unmerged work go in a stack, which the merge queue and the review gate both handle (ADR 0014); independent work branches from `main`. Each branch is made from the one below and its pull request opened into it, then `gh stack link <bottom> … <top>` (their numbers; `gh extension install github/gh-stack`) links them. A change below reaches those above by merging each branch into the next, bottom first, never by a rebase or a force-push. Martin merges a stack whole (`gh stack merge <stack> --squash`). The same holds in the app's repository. The `implement` skill's [Stacks](.claude/skills/implement/SKILL.md#stacks) has the rest.
- `deploy/` is GitOps: Argo CD deploys what is on `main`, so a change there reaches the cluster only when it merges. A deploy change that needs a new image (a migration, a new setting) waits for the pull request that pins that image.
- Admission control (ADR 0010) admits only images `build.yml` signed on `main`, and the few third-party images it names by digest, in `factory`, `runners`, `red-team`, `website`, `scoreboard` and `flagd` ([its copies](docs/COMPONENTS/ADMISSION-CONTROL.md)). To try an unmerged image on the local cluster, the `try-the-line` skill's `try begin` switches `factory-images` to audit for the run, and its `try end`, from any shell, puts it back and gives `root` its sync policy back. `website-images`, `scoreboard-images` and `flagd-images` are never switched: nothing built on the Mac runs in `website`, or beside the answer key, ever. A change to the app is tried in its own repository, and reaches the cluster through its pull request and its deploy. `make admission-ready` says whether every image the guarded namespaces run or will start would be admitted, the canary analysis's journeys Job in `website` included.
- A worker that takes work (triage, the red-team harness, the dependency sense, the traffic generator), run on the host, takes the cluster's copy's place: scale that one to nothing first, and back to one after. Never run the GitHub worker on the host without `GITHUB_DRY_RUN=true` while the cluster's runs: two that write never settle.
- Files listed in `.github/CODEOWNERS` are the rules of the line, and a change to one merges only with Martin's approval. When the work needs one changed, change it in the same pull request, keep to what the work needs, and give each file a line in a section of the description of its own: what changed and why. Never leave one stale, or file an issue for a change that belongs in the pull request.
- Merging is Martin's call, or the line's within what he set: only he, the line, or the GitHub worker, for this repository's local deploy pins and pin moves, adds a pull request to the merge queue. The line adds its own only when his autonomy level and auto-merge allow the review gate's rule for it ([the line's part](docs/COMPONENTS/APPROVAL-ROUTING.md#the-lines-part)); releases and improvements are always his. The worker adds the App's `deploy: local` pull request here once the gate passed its head as `exact-pin`, and the App's `pin` pull request from `factory/pin/<move>`, labelled by the App alone, once the gate passed it as `pin-move`, every required check green ([the worker's part](docs/COMPONENTS/APPROVAL-ROUTING.md#the-workers-part), ADR 0017); a pin move the gate held is Martin's to add, even once he approved it. The factory's App opens the deploy and release pull requests; no workflow opens, approves or queues one.
- The review gate passes the factory's App's pull requests by approval routing ([its rules](docs/COMPONENTS/APPROVAL-ROUTING.md)): exact pins, here a pin move it proves from the pull request (ADR 0019), and in the app's repository untagged changes. Lights-out, which also passes the App's tagged changes to the app, is the app's repository variable `AUTONOMY`, which only Martin sets. `GH_TOKEN="$(gh auth token)" AUTONOMY= mise exec -- node scripts/review-gate.ts --print <owner/name> <number>` says what the gate would of a pull request, and posts nothing; `GH_TOKEN="$(gh auth token)" AUTONOMY= mise exec -- node scripts/pin-moves.ts --print --as-app <owner/name> <number>` judges a pin move as if the App had opened it, working it out on the Mac, Trivy through Docker.
- The toolchain moves only when someone upgrades it: `mise upgrade`, which writes `mise.lock`, and both files in a `chore(toolchain)` pull request ([`CONTRIBUTING.md`](CONTRIBUTING.md#working-on-it) says how far each tool may move). Dependabot does not read mise.
- pnpm installs no release younger than a day, runs no dependency's install script unless `pnpm-workspace.yaml` allows it, and refuses a provenance downgrade. When it refuses, find out why; an exception goes in that file with its reason.
- Everything a repository runs or pins is on the vulnerability scan's list: `node apps/factory/src/vulnerabilities/inventory.ts <checkout>` prints it, and `--unlisted <checkout>` names every pin it does not read, which fails `make check` here. A new kind of pin is read there, in the same pull request.
- The daily scan (`vulnerabilities.yml`; `gh workflow run vulnerabilities.yml` runs it on `main`) puts its findings in each repository's code scanning; what to do about them is its moves, each a pin that moves, what it clears, its deadline and its lane (who moves it): `gh run download <run> -n moves` gives the day's `moves.json` ([moves](docs/COMPONENTS/SECURITY-SCANNING.md#moves), [patching](docs/COMPONENTS/PATCHING.md)).
- A finding that cannot reach us is excepted only in `policy/vulnerabilities.ts`, with an expiry at most 90 days off, in a pull request that also writes `osv-scanner.toml` again, which is Martin's to merge ([exceptions](docs/COMPONENTS/SECURITY-SCANNING.md#exceptions)). `make drill-vulnerability PACKAGE=… VERSION=… ADVISORY=… RATING=critical|lower` prints a drill's entries and pull requests, and opens nothing.
- Refresh a Dependabot pull request with `@dependabot rebase` or `@dependabot recreate`. Don't close it: that tells Dependabot to skip the version.
- A bump of `@anthropic-ai/claude-agent-sdk` merges only after a bench run on Claude ([`factory line bench`](docs/ON-THE-HOST.md#the-bench)) on the bumped package: the SDK is the agent loop every step runs in, and the tests replay cassettes, so a change in it shows only on a live step.
- A follow-up with no home yet is a [GitHub issue](https://github.com/the-roganator/cv-software-factory/issues) (`/issue` drafts one to the standard), on the milestone it waits for if it has one; never a code comment.
- Working notes that must never be committed (handovers, soak logs, drafts) go in `scratch/`. Git ignores it; `.ignore` keeps it searchable.
- The main checkout is shared, by Martin and by other sessions: nothing a session or its sub-agents run there changes its HEAD, index or tree (no `checkout`, `switch`, `reset`, `stash`, `pull` or `apply`), but for `git pull --ff-only` on `main` with a clean tree, which brings it up to date for `make up` or `make guardrails`. Work is done in a worktree of its own, under `scratch/worktrees/`, and another ref is read with `git show <ref>:<path>`.
