# Approval routing

Sends risky changes to a human. Part of the [GitHub plane](README.md#github-plane).

- **v1:** the line adds its own pull request to the merge queue when the gate's rule, Martin's autonomy level and auto-merge allow, and otherwise holds it in Needs you, saying why ([the line's part](#the-lines-part)); the GitHub worker adds the factory's own deploy pin, and the pin watch's moves by the same table ([the worker's part](#the-workers-part)); one required check, `review`, posted by the review App from `main`'s copy of `review.yml`, works out a pull request's risk tags from its diff and passes it by one rule or holds it for Martin ([ADR 0014](../architecture/adr/0014-merge-queue-and-review-gate.md#how-the-gate-routes)), a move of the daily scan's among them, which the gate makes itself and compares with the pull request ([a move](#a-move)); the planner's `out-of-scope` holds a spec before any code is written.

## The gate

`scripts/review-gate.ts` reads only GitHub's API and GHCR, never checking out the pull request, and decides by `scripts/review-routing.ts`; what it needs of a move, which reads the pull request's commits and the scan's moves, another job works out for it ([a move](#a-move)). Both, the workflow that runs them, the move's own scripts (`scripts/move.ts`, `scripts/moves.ts`, `scripts/derive.ts`) and the verdict's shape (`policy/review-verdict.ts`) are Martin's by CODEOWNERS.

| Tag | Given by |
|---|---|
| `test-loosening` | each test that test integrity excused as one the spec contradicts, from the warning it annotates each with on its `gates / test integrity` run |
| `dependency-change` | a lockfile or package manifest (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and the like), or `.npmrc` or `.pnpmfile.cjs`, which say where packages come from and what runs as they install, anywhere |
| `security-headers` | the app's header settings, `src/headers.ts`; or a line added or removed anywhere in the app's `src/` (not its tests) that names a security header in any case (`Content-Security-Policy` and its `-Report-Only`, `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, the three `Cross-Origin-*-Policy`) or `SECURITY_HEADERS`, so a header set outside that file is caught too; or such a file GitHub gives no patch of |
| `code-owned` | a path CODEOWNERS on `main` gives Martin; or a diff too large for GitHub to list whole |
| `release` | release-please's branch, or a change to a release's files alone |
| `improvement` | the app's typed list of flag names, `src/flag-names.ts`; or a line of the app's code (`src/`, not its tests), added or removed, that names `flag` or calls `.on(`; or such a file GitHub gives no patch of |
| `out-of-scope` | the planner or the reviewer, on the spec: held before the coder starts, in every mode (`ALWAYS_HELD`, `line/machine.ts`; [holds](ORCHESTRATOR.md#holds-and-martins-answers)). Not in a diff. |

The rule, the first that holds:

| Rule | Passes |
|---|---|
| `martin-opened` | a pull request Martin opened from a branch here |
| `martin-approved-head` | one whose head Martin's latest verdict approves: a push after his approval needs it again |
| `exact-pin` | the factory's App's, every changed line a `digest:` under `deploy/`, each image signed by its repository's `build.yml` on `main` (cosign), from a commit `ahead` of the pin it replaces |
| `move` | one from a branch here into `main`, in either repository and whoever opened it, that is exactly moves the daily scan of `main` asked for and nothing else, made by the gate and compared with what the merge makes ([below](#a-move)) |
| `major` | the same, when one of the moves it carries crosses a major and clears no Critical by Trivy's own rating |
| `low-risk` | the factory's App's, in the app's repository, with no tags and a successful test-integrity run by GitHub Actions at its head |
| `lights-out` | the same with tags, while the app's `AUTONOMY` variable is `lights-out`, but never with `release`, `improvement` or `code-owned` |
| `held` | anything else, saying why |

A risk label removed by anyone but Martin holds the pull request from every rule after his, whoever opened it. In this repository, the App's pull requests pass only as exact pins or moves, whatever `AUTONOMY` says. A missing, pending, skipped, cancelled or failed test-integrity run holds the App's pull request, and only GitHub Actions' latest run for the head, the one with the highest id, is read (an older attempt left unfinished is passed over; while the latest is unfinished, there is no reading yet), and only when its notice of what it judged ([test integrity](TEST-INTEGRITY.md#tests-the-spec-contradicts)) names this pull request, into the base it has now. The run reads the description of the pull request it judged, so another pull request's run at the same head, from another branch, open or closed, which read its own, is never this one's (a wait, as its own may yet run again), and a run that judged it into another base before it was retargeted, or says nothing of what it judged, holds it; so does one of a pull request that changes `.github/`, or that is into a branch other than `main`, either of which would be a workflow other than `main`'s. An exact pin needs every file GitHub lists, and a digest only one image entry has. A change of digests alone under `deploy/` passes only as an exact pin, in the app's repository too, and when it is not one (a signature cosign does not verify, an image GHCR does not have, a pin that goes backwards) it is held saying why, never judged by its tags.

A check the gate could not make is no judgement. When GitHub, GHCR or Sigstore does not answer (a network error, a timeout, a server's error, or cosign failing for one of those rather than finding no matching signature), the gate tries the exact pin's check again after 5, 15 and 30 seconds, each try only if it would end within three minutes of the gate starting (one window for the run, so the job's five minutes hold it). An answer a later try would not change (GitHub or GHCR answering 403 or 404, cosign missing) is not tried again, and holds the pull request saying so, as a read of GitHub that failed does. If it still cannot check it, the pull request is held, never passed and never judged by its tags, with a title that says so and why (`Not judged yet: the gate could not check its exact pin: …`), marked `pending` ([the verdict](#the-verdict)) so the line waits rather than take it for a refusal. Nothing runs the gate again for it: a push, a review or a re-run of the gate's last run settles it, and otherwise the line's bound ends the wait, holding it for Martin as having no verdict. When the review App's latest `review` check on the same commit passed, judging the same pull requests at the same heads, each held now for that alone by `exact-pin` and none of them with its base ever changed (which changes its pins at the same head), the gate posts nothing and that verdict stands, saying so in its log: a check that could not be made does not overturn one that was, so the merge queue keeps an entry whose commit the gate judged again (in the app's repository it does so when the gates finish) and could not check this time. Any other hold is posted as before.

## Who reads which signal

- **The gate** reads the diff, CODEOWNERS on `main`, Martin's reviews, the pull request's label events, test integrity's run, the caller's `AUTONOMY` variable, and, through its `move` job, the daily scan's moves of `main` and the state it sealed ([a move](#a-move)). Test integrity writes its notice of what it judged at the factory's commit the app's gates are pinned to, so the app moves that pin to one that writes it no later than it moves its pin of `review.yml` to one that reads it; otherwise every App pull request there is held, its run saying nothing of what it judged. It cannot read the factory's store, and merges nothing: a pull request merges only once someone adds it to the merge queue.
- **The line** reads the store's autonomy level and auto-merge switch (Martin's controls), the gate's verdict from the review App's own `review` check on the pull request's current head, whether the pull request conflicts with main, and the merge queue's word on what it added. It adds the app's deploy pull request to the queue only as an exact pin, and its own pull request only when auto-merge is on, the gate's rule is one the level allows, and the head is the one its own gates and reviewer passed; never an improvement, a release, a red-team branch or a work item whose spec was tagged `out-of-scope`. So the stricter of the two always wins: a fault in the line cannot merge what the gate fails, and the gate alone merges nothing.
- **The GitHub worker** reads the same two controls from the store before it adds a move, and the gate's verdict as the line does ([the worker's part](#the-workers-part)).

## The line's part

| Level | Rules a pull request is added to the merge queue by, with auto-merge on (`ENQUEUES`, `policy/line.ts`), for the line and the GitHub worker alike |
|---|---|
| Supervised | none |
| Guarded | `low-risk`, `exact-pin`, `move`, `martin-approved-head` |
| Lights-out | Guarded's, `major` and `lights-out` |

The line adds the app's deploy pull request, which the App opens and every fix waits for at Release, to the queue the same way, once its checks have passed: only when the gate passed its head as `exact-pin`, at Guarded or Lights-out with auto-merge on, once for each head. Otherwise it waits for Martin, and the line records why ([the line adds it to the queue](RELEASE-AND-VERIFY.md#the-line-adds-it-to-the-queue)). The factory's own local deploy pull request the GitHub worker adds to the queue at every level, whatever the switch says, once the gate passed its head as `exact-pin`; the pin watch's pull requests it adds by this table, once the gate passed the head as `move` or `major` and every required check is green ([below](#the-workers-part)).

Anything else is held in Needs you, as a `merge` hold naming the gate's rule, its tags with what gave each, its words, and why the line does not merge it; where Martin's approval of the head on GitHub would send it to the queue, the hold says so. Only a pull request the gate refused (`held`) is recorded as a refusal, `review-gate`, once for each head, signed by the GitHub worker. A merge held because the level or auto-merge does not allow it is his ordinary merge.

A hold the gate marks `pending` ([the verdict](#the-verdict)) is a wait, not a refusal: the line records nothing and holds nothing, and the change waits at Review for the gate to judge again (a hold already in force stands). The gate marks a hold pending conservatively, and the line, which has a clock, bounds the wait. Should the gate's latest verdict on the head still be pending fifteen minutes after the later of the line's own gates passing at that head and the pending check concluding (`PENDING_LIMIT_MS`; the gates' time is the store's for the line's `gates.finished`, so a restart neither starts it again nor ends it, and a re-run of test integrity, which has the gate judge again, starts it again), the merge is held for Martin as having no verdict (`no-verdict`), saying what the gate waits for, with nothing refused. The line reads the verdict before its gates pass at the head only with a hold in force, as after Martin's push; then the wait is timed from the check alone. A change whose gates never finish, as when test integrity never starts, stands at Gates, and the line's stuck alert pages for it. No hold made while the verdict is pending, a conflict or the queue's among them, carries its words, rule, tags or check, and the verdict resolving does not make a conflict's or the queue's hold again. A passing verdict is never stale: `low-risk` already needs a completed, successful test-integrity run, and Martin's approval and an exact pin do not depend on one. A pass given before test integrity is run again at the same head is still enqueued; `gates / test integrity` is among the app's required checks (`scripts/github-settings.ts`), which the merge queue requires of its own commit, so a re-run that fails there stops the merge, and the queue taking it out holds it as below. The queue taking a pull request out is recorded (`pull-request.dequeued`), with the checks that failed. Taken out because a check failed on the queue's commit, the line adds the same head again, three times in all (`QUEUE_TRIES`, counted from those events), as [the worker](#the-workers-part) adds its own; the third time, or taken out any other way, it holds it, and out of tries says so on the pull request once. [The line's merge](ORCHESTRATOR.md#the-merge) has the rest.

`AUTONOMY` is a variable of the app's repository, which only Martin can set: `gh variable set AUTONOMY -R the-roganator/cv-worlds-worst-website -b lights-out`, and `gh variable delete AUTONOMY -R the-roganator/cv-worlds-worst-website` to go back. It decides only the `lights-out` rule for the App's tagged changes there: no move reads it, and this repository's is never read.

### A move

`scripts/move.ts` ([ADR 0022](../architecture/adr/0022-the-gate-passes-exactly-the-scans-moves.md)) passes a pull request into `main` from a branch of the repository's own, in either repository and whoever opened it, that Martin has not passed and that is no exact pin, when it is exactly moves the daily scan of `main` asked for and nothing else. Who opened it decides only who queues it.

The gate takes the scan's moves from the newest finished run of `vulnerabilities.yml` on `main`, by schedule, push or hand, in the repository itself: its `moves.json`, joined with the state that run sealed ([the state](SECURITY-SCANNING.md#the-state)) as the GitHub worker joins them, so a lockfile's move has its package and versions. Nothing a pull request can change. It makes on `main`'s tip (for the merge queue's commit, on the commit it was made on) each move the pull request carries, as the one who makes it makes it: a pin's line by the pin watch's own edit (an image's tag and digest, a chart's version, k3s's release); a lockfile's package, an image that brings another pin with it (the Node it runs, or Playwright's library), and in the factory anything mise pins, by the pin step (`writePins`, `apps/runner/src/pins.ts`), run on a checkout of `main`'s tip with the pnpm and mise this repository pins, no script, no pnpmfile and `main`'s files alone (`scripts/derive.ts`). It makes them as the scan made them, in either repository: as of the scan's time, and with the digest that run's `pins` job was given for each tag it asked ([the moves the scan makes](SECURITY-SCANNING.md#moves)), a tag it never asked asked of its registry now. The app's line makes its moves from the same time and answers ([the pin step](AGENT-RUNNERS.md#the-pin-step)); nothing a pull request carries says how it was made. An image's target is always the digest the scan named. Then it compares the result with what the merge makes (the head merged onto `main`'s tip from their merge base), every file the merge changes and every file the moves write, byte for byte.

A pull request carries a move when it rewrites a line one of the move's pins is on (a lockfile's move's, where the scan found its package). It may carry several of the day's moves, and must carry each whole. Anything that differs is refused, and the gate says where: a line no move writes, a pin left unmoved, a version or digest other than the scan's, a file added, removed or changed in mode, one that is not UTF-8 text, anything under `.github/`, a head that does not merge onto `main` without a conflict, a move the pin step cannot make on `main`, or an image of ours, which passes only as an exact pin. What a lockfile's move withholds is never said: a file the derivation writes is named by its line alone. A pull request refused so, or one that touches no pin of the scan's moves, is then judged by the rest of the rules, which in this repository hold the App's.

Every fact the verdict names comes from the scan's move, never from the pull request: where its pins are, what it moves to, whether it crosses a major, and what it clears. The rule is `major` when one of the moves it carries crosses a major and clears no Critical by Trivy's own rating, as the state gives each finding, and `move` otherwise: the publisher's rating, which the move's counts and deadline take where it is higher, may hold a major and never releases one, and Node's own advisories, which only Node rates, release none (`namedMajor`, `github/made.ts`). The rule holds whatever the pull request's tags, which name the pins' own files (`dependency-change`, or `code-owned` on mise's files or a `Dockerfile`). The gate reads no level and no `AUTONOMY`: who queues each rule is `ENQUEUES`. Whether the checks pass is not the gate's either: the merge queue requires every required check, and the GitHub worker waits for them before it adds a move.

Working a move out reads the pull request's head, as data, which the job holding the review App's key never does. `review.yml`'s `move` job does it (`scripts/moves.ts`), with read-only permissions (`contents`, `pull-requests`, and `actions` for the scan's artifacts), no key of the App's, `main`'s whole checkout and its locked dependencies, fetching the pull request's commits and running none of them, and hands the gate one answer for each pull request it would judge, by number and head (`MOVES`), within twelve minutes of starting. It holds one secret, the scan's state key (`SCAN_STATE_KEY`), from the `scan-state` environment, which only `main` may use; it reads the key once and takes it out of its environment before anything runs, and a repository that calls the gate passes it by name, as it passes the review App's key. The gate takes an answer only for that pull request at that head: a head the job did not judge (pushed while it waited for a runner) is a pending hold, which the run its push started settles ([the verdict](#the-verdict)), and answers the gate cannot read are no move. `review-gate.ts --print` judges no move; `moves.ts --print` replays a pull request with the move worked out on the Mac, from that repository's last scan of `main`, and posts nothing:

```sh
GH_TOKEN="$(gh auth token)" AUTONOMY= SCAN_STATE_KEY="$(kubectl --context k3d-software-factory -n factory get secret scan-state-key -o 'jsonpath={.data.cv-software-factory}' | base64 -d)" mise exec -- node scripts/moves.ts --print --as-app the-roganator/cv-software-factory <number>
```

## The worker's part

The GitHub worker adds this repository's local deploy pull request to the merge queue itself, at any autonomy level and whether the line runs or not ([ADR 0017](../architecture/adr/0017-the-worker-queues-the-local-deploy-pins.md), `github/deploy-queue.ts`), when all of these hold:

- the App opened it, from `deploy/local` into `main`, not a draft, labelled `deploy: local`, with the title the deploy watch writes;
- the review App's `review` check on that head passed it as `exact-pin`: no other rule, and never a hold, a pending one, or a verdict for another head;
- every other check `main`'s rulesets require has a latest run on the head that finished and did not fail, by anyone but the factory's App;
- it does not conflict with `main`, and is not queued already.

It adds the pin watch's pull requests ([the pins](GITHUB-WORKER.md#pins)) on the same terms, each open one on its own, with these in place of the first two:

- the App opened it, from this repository's `factory/pin/<files>` (one segment) into `main`, not a draft, labelled `pin`, and nobody but the App ever gave it that label or took it off, by its events (Martin holds one by taking the label off): the gate trusts no branch, so a move on any other branch passes the gate and is still not queued;
- the review App's `review` check on that head passed it as `move` or `major`: never another rule, so never a hold, and never `martin-approved-head`, his approval of a head the gate held, which leaves adding it his;
- the autonomy level and auto-merge Martin set, read from the store just before the enqueue, queue that rule (`enqueues`, the table [above](#the-lines-part)): a `move` at Guarded or Lights-out, a `major` at Lights-out alone, each with auto-merge on. Controls the worker cannot read are Supervised with auto-merge off ([the level](GITHUB-WORKER.md#the-deploy-queue)).

The gate names what a move is, and the level decides; the gate does not refuse a `major`, so the worker's reading of the level is what keeps one from the queue below Lights-out, and the App's key alone could queue an exact major at Guarded. What stands behind that merge is the gate's proof that it is exactly the scan's move, the required checks, signed images, admission, the canary and rollback. A move the level or the switch holds waits with nothing in Needs you: the worker logs why, and a major's description says it waits for Martin and what to do.

It enqueues at that head, through the line's action and guards (`enqueuePullRequest`). A failure that may pass (the head moved, a rate limit, an outage) is tried again on the next pass, up to five times; a refusal, the guard's or GitHub's 403, is kept, signed and logged as the worker keeps its others, and it or any other failure leaves the head for Martin.

It adds a head once, unless the queue takes it out because a check failed on the queue's commit. That may be a flake, so the worker adds the head again on its next pass, while all of the above still holds, three times in all (`QUEUE_TRIES`). It does not judge why the check failed: a change that breaks `main` fails every time. After the third failure at one head, counted from GitHub's record of the pull request, it stops and says so in a comment on the pull request, naming the checks that failed last, and that head is Martin's. A head that left the queue any other way (he took it out, or it conflicted) is his too, with no second try.

A required check can fail on the pull request's own head for the same reasons, before the queue sees it, and a job that hangs is cancelled by its time limit and fails. Once the gate passed the head and every required check there has finished, the worker writes the watch's commit again (`commitAgain`): the same tree on the same parent, by the App as before, its message the same but for a `Checks-run:` line. That is a new head, which GitHub runs every check and the gate on afresh, and the worker records it as the watch's. It starts no run itself: the App's Actions permission is read only. A commit has three runs of its checks in all (`RUN_TRIES`), counted from the head's own message, so a restart does not start the count again. Then it says so once in a comment on the pull request, naming the checks that failed, and the head is Martin's; a check he runs again and passes lets it go on. A failed check another app posted is not run again this way.

In a dry run the watches write nothing to GitHub, so no head there is one they wrote, and the worker adds and records no enqueue. The app's deploy pull request stays the line's, a release and anything else Martin's.

## The verdict

The check's summary has a line for each pull request it judged, with its rule and each tag with what gave it, which Needs you shows, and a block the line parses with `readVerdict` (`policy/review-verdict.ts`):

```
<!-- review-verdict v1
{"commit":"<the commit the check is on>","judged":[{"number":7,"head":"<sha>","rule":"held","tags":[{"tag":"dependency-change","because":["pnpm-lock.yaml"]}]}]}
-->
```

A `held` entry carries `pending`, at most 300 characters (code points, cut once, where the summary is written) saying what it waits for, exactly when the gate could not check the App's exact pin, with nothing it did read holding it ([above](#the-gate)), when the `move` job did not judge the pull request at its head ([a move](#a-move)), or when all of these hold: the App's pull request is in the app's repository, into `main`, changes nothing under `.github/`, has no risk label removed and no tag the level would not pass, and GitHub Actions has posted no `gates / test integrity` run for its head, or its latest run for the head (the one with the highest id, a queued re-run included) has not completed, or that latest run judged another pull request. A run of that name only another app posted is never read and counts as none, so it is pending too: nothing the gate can trust has arrived yet. The gate is run again when the gates finish, a pin it could not check is settled by its next run, whatever starts it, and a head the move job did not judge by the run its push started, so a pending hold is a wait, not a refusal, and its words say what it waits for. The gate marks it conservatively, and the line, which has a clock, bounds the wait: if no verdict comes within its limit, the line holds the work item for Martin. Every other hold carries none, whatever test integrity's state, and stays a hold until Martin's approval or the next judgement clears it: a tag the level does not pass (held for those tags, by name, its title naming test integrity's reading too when there is none, even while test integrity runs), a removed risk label, a change under `.github/`, a base other than `main` (a stacked pull request), a latest run that completed and failed, was cancelled or was skipped, or that judged this pull request into another base or says nothing of what it judged, or whose annotations GitHub gave fewer or more of than it counts, a read of GitHub that failed, and anything in this repository but an exact pin or a move. At Lights-out a pending verdict may be judged again as a hold for tags: test integrity's reading can add `test-loosening`, which Lights-out never passes. The field is optional, so the block is still version 1.

Read it only from the check named `review` that the review App (5470762) posted for the pull request's current head: the factory's App can post check runs too. A summary with no block, two, or one that does not parse whole (`pending` beside a passing rule among it) carries no verdict.

To see what the gate would say of a pull request, with nothing posted:

```sh
GH_TOKEN="$(gh auth token)" AUTONOMY= mise exec -- node scripts/review-gate.ts --print the-roganator/cv-worlds-worst-website <number>
```
