# Approval routing

Sends risky changes to a human. Part of the [GitHub plane](README.md#github-plane).

- **v1:** the line adds its own pull request to the merge queue when the gate's rule, Martin's autonomy level and auto-merge allow, and otherwise holds it in Needs you, saying why ([the line's part](#the-lines-part)); one required check, `review`, posted by the review App from `main`'s copy of `review.yml`, works out a pull request's risk tags from its diff and passes it by one rule or holds it for Martin ([ADR 0014](../architecture/adr/0014-merge-queue-and-review-gate.md#how-the-gate-routes)); the planner's `out-of-scope` holds a spec before any code is written.
- **Later:** a Critical vulnerability's fix passing under Guarded (Part D).

## The gate

`scripts/review-gate.ts` reads only GitHub's API and GHCR, never checking out the pull request, and decides by `scripts/review-routing.ts`; what it needs of a pin move, or in the app of a Critical fix, each of which reads the pull request's commits, another job works out for it ([a pin move](#a-pin-move), [a Critical fix](#a-critical-fix)). Both, the workflow that runs them, and the verdict's shape (`policy/review-verdict.ts`) are Martin's by CODEOWNERS.

| Tag | Given by |
|---|---|
| `test-loosening` | each test that test integrity excused as one the spec contradicts, from the warning it annotates each with on its `gates / test integrity` run |
| `dependency-change` | a lockfile or package manifest (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and the like), or `.npmrc` or `.pnpmfile.cjs`, which say where packages come from and what runs as they install, anywhere |
| `security-headers` | the app's header settings, `src/headers.ts`; or a line added or removed anywhere in the app's `src/` (not its tests) that names a security header in any case (`Content-Security-Policy` and its `-Report-Only`, `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, the three `Cross-Origin-*-Policy`) or `SECURITY_HEADERS`, so a header set outside that file is caught too; or such a file GitHub gives no patch of |
| `code-owned` | a path CODEOWNERS on `main` gives Martin; or a diff too large for GitHub to list whole |
| `release` | release-please's branch, or a change to a release's files alone |
| `improvement` | the app's typed list of flag names, `src/flag-names.ts`; or a line of the app's code (`src/`, not its tests), added or removed, that names `flag` or calls `.on(`; or such a file GitHub gives no patch of |
| `out-of-scope` | the planner or the reviewer, on the spec: held before the coder starts, in every mode (`ALWAYS_HELD`, `line/machine.ts`; [holds](ORCHESTRATOR.md#holds-and-martins-answers)). Not in a diff. |

The rule, the first that holds:

| Rule | Passes |
|---|---|
| `martin-opened` | a pull request Martin opened from a branch here |
| `martin-approved-head` | one whose head Martin's latest verdict approves: a push after his approval needs it again |
| `exact-pin` | the factory's App's, every changed line a `digest:` under `deploy/`, each image signed by its repository's `build.yml` on `main` (cosign), from a commit `ahead` of the pin it replaces |
| `pin-move` | the factory's App's, in this repository, into `main`: one pin of the vulnerability scan's list moved forward on its line, proved from the pull request ([below](#a-pin-move)) |
| `critical-fix` | the factory's App's, in the app's repository, into `main`: one dependency moved to fix a finding the gate's own scanner rates Critical, its pins alone changed, proved from the pull request, whatever `AUTONOMY` says ([below](#a-critical-fix)) |
| `low-risk` | the factory's App's, in the app's repository, with no tags and a successful test-integrity run by GitHub Actions at its head |
| `lights-out` | the same with tags, while the app's `AUTONOMY` variable is `lights-out`, but never with `release`, `improvement` or `code-owned` |
| `held` | anything else, saying why |

A risk label removed by anyone but Martin holds the pull request from every rule after his. In this repository, the App's pull requests pass only as exact pins or pin moves, whatever `AUTONOMY` says. A missing, pending, skipped, cancelled or failed test-integrity run holds the App's pull request, and only GitHub Actions' latest run for the head, the one with the highest id, is read (an older attempt left unfinished is passed over; while the latest is unfinished, there is no reading yet), and only when its notice of what it judged ([test integrity](TEST-INTEGRITY.md#tests-the-spec-contradicts)) names this pull request, into the base it has now. The run reads the description of the pull request it judged, so another pull request's run at the same head, from another branch, open or closed, which read its own, is never this one's (a wait, as its own may yet run again), and a run that judged it into another base before it was retargeted, or says nothing of what it judged, holds it; so does one of a pull request that changes `.github/`, or that is into a branch other than `main`, either of which would be a workflow other than `main`'s. An exact pin needs every file GitHub lists, and a digest only one image entry has. A change of digests alone under `deploy/` passes only as an exact pin, in the app's repository too, and when it is not one (a signature cosign does not verify, an image GHCR does not have, a pin that goes backwards) it is held saying why, never judged by its tags.

A check the gate could not make is no judgement. When GitHub, GHCR or Sigstore does not answer (a network error, a timeout, a server's error, or cosign failing for one of those rather than finding no matching signature), the gate tries the exact pin's check again after 5, 15 and 30 seconds, each try only if it would end within three minutes of the gate starting (one window for the run, so the job's five minutes hold it). An answer a later try would not change (GitHub or GHCR answering 403 or 404, cosign missing) is not tried again, and holds the pull request saying so, as a read of GitHub that failed does. If it still cannot check it, the pull request is held, never passed and never judged by its tags, with a title that says so and why (`Not judged yet: the gate could not check its exact pin: …`), marked `pending` ([the verdict](#the-verdict)) so the line waits rather than take it for a refusal. Nothing runs the gate again for it: a push, a review or a re-run of the gate's last run settles it, and otherwise the line's bound ends the wait, holding it for Martin as having no verdict. When the review App's latest `review` check on the same commit passed, judging the same pull requests at the same heads, each held now for that alone by `exact-pin` and none of them with its base ever changed (which changes its pins at the same head), the gate posts nothing and that verdict stands, saying so in its log: a check that could not be made does not overturn one that was, so the merge queue keeps an entry whose commit the gate judged again (in the app's repository it does so when the gates finish) and could not check this time. Any other hold is posted as before.

## Who reads which signal

- **The gate** reads the diff, CODEOWNERS on `main`, Martin's reviews, the pull request's label events, test integrity's run, and the caller's `AUTONOMY` variable. Test integrity writes its notice of what it judged at the factory's commit the app's gates are pinned to, so the app moves that pin to one that writes it no later than it moves its pin of `review.yml` to one that reads it; otherwise every App pull request there is held, its run saying nothing of what it judged. It cannot read the factory's store, and merges nothing: a pull request merges only once someone adds it to the merge queue.
- **The line** reads the store's autonomy level and auto-merge switch (Martin's controls), the gate's verdict from the review App's own `review` check on the pull request's current head, whether the pull request conflicts with main, and the merge queue's word on what it added. It adds the app's deploy pull request to the queue only as an exact pin, and its own pull request only when auto-merge is on, the gate's rule is one the level allows, and the head is the one its own gates and reviewer passed; never an improvement, a release, a red-team branch or a work item whose spec was tagged `out-of-scope`. So the stricter of the two always wins: a fault in the line cannot merge what the gate fails, and the gate alone merges nothing.

## The line's part

| Level | Rules the line merges by, with auto-merge on (`ENQUEUES`, `policy/line.ts`) |
|---|---|
| Supervised | none |
| Guarded | `low-risk`, `exact-pin`, `critical-fix`, `martin-approved-head` |
| Lights-out | Guarded's, and `lights-out` |

The line adds the app's deploy pull request, which the App opens and every fix waits for at Release, to the queue the same way, once its checks have passed: only when the gate passed its head as `exact-pin`, at Guarded or Lights-out with auto-merge on, once for each head. Otherwise it waits for Martin, and the line records why ([the line adds it to the queue](RELEASE-AND-VERIFY.md#the-line-adds-it-to-the-queue)). The factory's own local deploy pull request, and the pin watch's pull request for each move, the GitHub worker adds to the queue, whatever the level, once the gate passed its head as `exact-pin` or `pin-move` respectively and every required check is green ([below](#the-workers-part)).

Anything else is held in Needs you, as a `merge` hold naming the gate's rule, its tags with what gave each, its words, and why the line does not merge it; where Martin's approval of the head on GitHub would send it to the queue, the hold says so. Only a pull request the gate refused (`held`) is recorded as a refusal, `review-gate`, once for each head, signed by the GitHub worker. A merge held because the level or auto-merge does not allow it is his ordinary merge.

A hold the gate marks `pending` ([the verdict](#the-verdict)) is a wait, not a refusal: the line records nothing and holds nothing, and the change waits at Review for the gate to judge again (a hold already in force stands). The gate marks a hold pending conservatively, and the line, which has a clock, bounds the wait. Should the gate's latest verdict on the head still be pending fifteen minutes after the later of the line's own gates passing at that head and the pending check concluding (`PENDING_LIMIT_MS`; the gates' time is the store's for the line's `gates.finished`, so a restart neither starts it again nor ends it, and a re-run of test integrity, which has the gate judge again, starts it again), the merge is held for Martin as having no verdict (`no-verdict`), saying what the gate waits for, with nothing refused. The line reads the verdict before its gates pass at the head only with a hold in force, as after Martin's push; then the wait is timed from the check alone. A change whose gates never finish, as when test integrity never starts, stands at Gates, and the line's stuck alert pages for it. No hold made while the verdict is pending, a conflict or the queue's among them, carries its words, rule, tags or check, and the verdict resolving does not make a conflict's or the queue's hold again. A passing verdict is never stale: `low-risk` already needs a completed, successful test-integrity run, and Martin's approval and an exact pin do not depend on one. A pass given before test integrity is run again at the same head is still enqueued; `gates / test integrity` is among the app's required checks (`scripts/github-settings.ts`), which the merge queue requires of its own commit, so a re-run that fails there stops the merge, and the queue taking it out holds it as below. The queue taking a pull request out is recorded (`pull-request.dequeued`), with the checks that failed, and holds it. [The line's merge](ORCHESTRATOR.md#the-merge) has the rest.

`AUTONOMY` is a variable of the app's repository, which only Martin can set: `gh variable set AUTONOMY -R the-roganator/cv-worlds-worst-website -b lights-out`, and `gh variable delete AUTONOMY -R the-roganator/cv-worlds-worst-website` to go back. This repository's is never read.

### A pin move

`scripts/pin-move.ts` ([ADR 0019](../architecture/adr/0019-the-gate-passes-a-pin-move-it-proves.md)) passes the App's pull request here into `main`, never retargeted (by anyone, or by GitHub when its base branch went), whose head no other pull request has had and whose branch no other has come from since it was opened, tried after the exact pin, when it proves each of these on what the merge makes (its head merged onto `main`'s tip, against that tip), in this order, and otherwise holds it, the first reason it could not prove named in the hold beside the exact pin's (`Not an exact pin (…), nor a pin move: …`):

| Condition | Proved by |
|---|---|
| Pins only | every file modified in place, regular, with its mode, line for line, each line only in versions and digests; nothing under `.github/`, neither `mise.toml` nor `mise.lock`; the list (`inventory.ts`) the same at both but in one move's pins, one image, chart or chart's value from one pin to one other; every changed line one of them, its old text with the pin's span alone replaced; `--unlisted` empty at the head |
| Not what judges | not Trivy's, Syft's or Kyverno's pin |
| Signed where its publisher signs | not an image of ours, which passes only as an exact pin; a third-party image by its digest, below |
| Forward on its line | the tag's index digest now, at the same tag or the newest on its line (`newestOf`, as the scan resolves a fix), never back or a major; a chart's later release on its major, never a prerelease, in its repository's index; each image a chart's new version runs in place of an old one on a version tag, the same or later, on its major, at the tag's digest now where the chart pins one |
| No record goes stale | each refusal record's policy hash (`policy-hash.ts`, `main`'s) the same at both |
| Nothing else that runs changes | a chart's, a value's or `deploy/`'s rendering, a chart rendered as Argo CD renders it (its namespace, its `crds/`, the k3s `main` pins, `main`'s `deploy/k3d/api-versions.json`), compared object by object (kind, namespace, name), has the same objects at both, the same but for each moved image's `from` at the base for its `to` at the head, the chart's version labels moving as the chart's where nothing selects by them, a core ConfigMap's `data`, and a core workload's pod template's `checksum/` annotations; every character tab, LF or printable but CR, U+0085, U+2028, U+2029 and the byte order mark; split on `---` alone, as the cluster splits it, and read as YAML 1.2 and 1.1, holding on what readers may read apart (a document a `...` begins, a directive, tag, anchor, alias, merge key, duplicate key or key that is no string, a List, two documents with one key); the hold names the object and field; and every line outside those ConfigMaps' `data` and those annotations, as the gate's parser places them, the base's line in order, the moved images and the version labels that moved as the chart's written alike |
| The scans show it | the pinned Trivy, on a fresh database, on the image before and after on `linux/amd64` and `linux/arm64`, each apart: a finding (its advisory and package) with a fix gone, nothing new at High or above, each scan having read something |
| Something ran it | every run at the head succeeded at its latest attempt, of the job in the workflow that has it (its check suite's run of this repository's file, on the pull request, from its own branch, made no earlier than it): `ZAP scan` for ZAP's image, `image builds` for a Dockerfile's stage outside `deploy/`, each `tests` shard for Postgres, and `platform` (`platform.yml`) for what a cluster runs from the change, a chart, a value or a third-party image in `deploy/`, Postgres too, when a Deployment, StatefulSet or DaemonSet of the head's rendering, read as YAML, runs the moved image as a container, not a hook, above nought replicas, and not one the check's own patches change; a `platform` skipped made no cluster, and holds. Argo CD's chart and values, and `deploy/argocd/`, are `make up`'s and held, and k3s waits for Martin whatever `platform` says |

The head is data: its lines are read as text first, and only a change of versions and digests on the base's own lines is rendered or scanned. `review.yml`'s `pin move` job, with read-only permissions and no secret, works each answer out (`scripts/pin-moves.ts`) from `main`'s whole checkout and hands it to the gate by number and head (`PIN_MOVES`); the gate takes it only for that pull request at that head, and holds one with no answer, or answers it cannot read. A fact not read is a hold. The gate runs again when `check.yml` or `platform.yml` finishes, for a pin move held only because the job that runs its pin had not. `GH_TOKEN="$(gh auth token)" mise exec -- node scripts/pin-moves.ts --print --as-app <owner/name> <number>` replays a pull request as the App's, with no say of Martin's, and works the move out on the Mac with Docker.

### A Critical fix

`scripts/critical-fix.ts` ([ADR 0020](../architecture/adr/0020-the-gate-passes-a-critical-fix-it-proves.md)) passes the App's pull request in the app's repository into `main`, on the same terms of branch, head and base as a pin move, that carries `dependency-change` (or `code-owned` on its pins alone, as a Node move does) and is no exact pin, when it proves each of these on what the merge makes, in this order, and otherwise holds it with its tag, the first reason it could not prove named in the hold (`Held for its risk tags (dependency-change); not a critical fix: …`):

1. **Pins only:** `pnpm-lock.yaml`; a dependency's version range in `package.json`, a registry's, and nothing else of it; a `FROM` line's tag and digest, in the same image repository; `mise.toml`'s Node with its `mise.lock` entry, together and forward on its major. The lockfile, read as YAML, changes only its importers' ranges and versions, each a registry's, and its packages and snapshots, each package from the registry by its integrity, none gone, none changed at the same version, and each version that goes replaced by one forward of it on its major.
2. **Forward on its line:** each moved `FROM`, as a pin move's image (`imageForward`).
3. **The scans show the fix:** the gate's pinned Trivy, on a fresh database, on the lockfile and each moved image (both platforms) at both sides, and Node's own database on mise's Node at both sides: a finding the scanner rates Critical, with a fix, gone, its package still listed at or above the fix, every package the base lists still listed, and Node still named where it was. The publisher's rating is never read. Criticals fixed in two packages are a group, and held.
4. **Nothing new:** nothing at High or above in any scan of the head that the base's did not have.
5. **Only what the fix needs moves:** for a package, the packages its new version requires and no other, no other range, and no image or Node; for Node, mise and every `FROM`, each image whose Node is read on mise's; for an image's own package, that image alone.
6. **Every gate passes:** GitHub Actions' latest run at the head of each of the app's required checks but `review`, from the workflow that has its job, for this pull request. `image builds` runs the runtime image's `node --version` against mise's, which is how the distroless runtime's Node, which its tag does not name, is held to the Node scanned.

The tags it passes are `dependency-change`, and `code-owned` on `Dockerfile`, `mise.toml` and `mise.lock` alone; any other holds it. It passes whatever `AUTONOMY` says, as `low-risk` does, and the line queues it at Guarded and Lights-out with auto-merge on, and tells Martin of each such merge. Nothing of the head is built, installed or run: the lockfile and the images are scanned as data. `review.yml`'s `critical fix` job, in the app's repository alone, with read-only permissions (`actions: read` among them) and no secret, works each answer out (`scripts/critical-fixes.ts`) and hands it to the gate by number and head (`CRITICAL_FIXES`); the gate takes it only for that pull request at that head, and holds one with no answer. `GH_TOKEN="$(gh auth token)" mise exec -- node scripts/critical-fixes.ts --print --as-app <owner/name> <number>` replays a pull request as the App's, with Docker for Trivy.

## The worker's part

The GitHub worker adds this repository's local deploy pull request to the merge queue itself, at any autonomy level and whether the line runs or not ([ADR 0017](../architecture/adr/0017-the-worker-queues-the-local-deploy-pins.md), `github/deploy-queue.ts`), once for each head, when all of these hold:

- the App opened it, from `deploy/local` into `main`, not a draft, labelled `deploy: local`, with the title the deploy watch writes;
- the review App's `review` check on that head passed it as `exact-pin`: no other rule, and never a hold, a pending one, or a verdict for another head;
- every other check `main`'s rulesets require has a latest run on the head that finished and did not fail, by anyone but the factory's App;
- it does not conflict with `main`, and is not queued already.

It adds the pin watch's pull request for a move ([the pins](GITHUB-WORKER.md#pins)) on the same terms, each open one on its own, with these in place of the first two:

- the App opened it, from this repository's `factory/pin/<move>` (one segment) into `main`, not a draft, labelled `pin`, and nobody but the App ever gave it that label or took it off, by its events (Martin holds one by taking the label off): the gate trusts no branch, so a pin move's content on any other branch passes the gate and is still not queued;
- the review App's `review` check on that head passed it as `pin-move`: never another rule, so never a hold, and never `martin-approved-head`, his approval of a head the gate held, which leaves adding it his.

It enqueues at that head, through the line's action and guards (`enqueuePullRequest`). A failure that may pass (the head moved, a rate limit, an outage) is tried again on the next pass, up to five times; a refusal, the guard's or GitHub's 403, is kept, signed and logged as the worker keeps its others, and it or any other failure leaves the head for Martin, as does the queue taking it out. In a dry run the watches write nothing to GitHub, so no head there is one they wrote, and the worker adds and records no enqueue. The app's deploy pull request stays the line's, a release and anything else Martin's.

## The verdict

The check's summary has a line for each pull request it judged, with its rule and each tag with what gave it, which Needs you shows, and a block the line parses with `readVerdict` (`policy/review-verdict.ts`):

```
<!-- review-verdict v1
{"commit":"<the commit the check is on>","judged":[{"number":7,"head":"<sha>","rule":"held","tags":[{"tag":"dependency-change","because":["pnpm-lock.yaml"]}]}]}
-->
```

A `held` entry carries `pending`, at most 300 characters (code points, cut once, where the summary is written) saying what it waits for, exactly when the gate could not check the App's exact pin, with nothing it did read holding it ([above](#the-gate)), or when all of these hold: the App's pull request is in the app's repository, into `main`, changes nothing under `.github/`, has no risk label removed and no tag the level would not pass, and GitHub Actions has posted no `gates / test integrity` run for its head, or its latest run for the head (the one with the highest id, a queued re-run included) has not completed, or that latest run judged another pull request. A run of that name only another app posted is never read and counts as none, so it is pending too: nothing the gate can trust has arrived yet. The gate is run again when the gates finish, and a pin it could not check is settled by its next run, whatever starts it, so a pending hold is a wait, not a refusal, and its words say what it waits for. The gate marks it conservatively, and the line, which has a clock, bounds the wait: if no verdict comes within its limit, the line holds the work item for Martin. Every other hold carries none, whatever test integrity's state, and stays a hold until Martin's approval or the next judgement clears it: a tag the level does not pass (held for those tags, by name, its title naming test integrity's reading too when there is none, even while test integrity runs), a removed risk label, a change under `.github/`, a base other than `main` (a stacked pull request), a latest run that completed and failed, was cancelled or was skipped, or that judged this pull request into another base or says nothing of what it judged, or whose annotations GitHub gave fewer or more of than it counts, a read of GitHub that failed, and anything in this repository but an exact pin or a pin move. At Lights-out a pending verdict may be judged again as a hold for tags: test integrity's reading can add `test-loosening`, which Lights-out never passes. The field is optional, so the block is still version 1.

Read it only from the check named `review` that the review App (5470762) posted for the pull request's current head: the factory's App can post check runs too. A summary with no block, two, or one that does not parse whole (`pending` beside a passing rule among it) carries no verdict.

To see what the gate would say of a pull request, with nothing posted:

```sh
GH_TOKEN="$(gh auth token)" AUTONOMY= mise exec -- node scripts/review-gate.ts --print the-roganator/cv-worlds-worst-website <number>
```
