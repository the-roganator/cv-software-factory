# Console

The UI for visitors and admin (spec 5). Part of the [factory plane](README.md#factory-plane).

- **v1:** a single-page app written to React's API and run by Preact, built by Vite 8 (ADR 0007) in its own image stage.

Everyone gets the same page, drawn from the public events: the line, the reel, the Canary panel, Needs you, Controls, Flags, Spend, the settings and the audit log, with each of Martin's controls shown read-only beside what it does. Martin signs in with a passkey, and then his page reads the full events and changes the factory through the [admin service](ADMIN-SERVICE.md) alone: the console's own server only reads.

## The server

The Node server serves, to anyone, and with `GET` or `HEAD` alone:

- the build, by Vite's manifest;
- the public events, as JSON and as server-sent events resuming from `Last-Event-ID`;
- the artifacts public events refer to;
- whether each relayed refusal is what the GitHub worker signed (`GET /api/refusals`, `src/refusals.ts`), the one thing it says that is not an event or an artifact, because only it can: the check needs the record the GitHub worker kept, which holds the refusal's words before redaction, and the worker's public key, the ConfigMap `refusal-key` (`REFUSAL_PUBLIC_KEY`). For each public `action.refused` that carries a record and a signature, it opens the record by its hash, once, and answers by seq: **verified** when the bytes hash to that name, the signature over them verifies, and the public payload is the signed one with only what a relay adds beside it (the record and signature, a fold's count and last time, what was refused on no work item); **redacted** when the public payload is the signed one through the redactor, so its words differ only as the public view changes them; and **unverified** otherwise, or with no key. A record it could not read is left out of the answer, and read again when next asked. The page asks only about a refusal whose record is named by its hash, by the same test (`signedPayloadOf` in `@software-factory/events/signed`), and reads any other relayed one as unverified. Nothing of a record leaves it but that word. An event-log folder is what the replay site publishes whole, so it holds no record and no key: only each relayed refusal's check, made when it was written (`refusals.json`), which a page reading the folder reads, and the server serving a folder answers from (any it has none for is unverified). The live console never serves a record either: `/artifacts/:hash` serves only what a public event lists in its `artifacts`, and a relayed refusal names its record in its payload.

It writes into the page the profile whose policy bounds Martin's settings and whether the gateway sends every agent to the local model, from the `FACTORY_PROFILE` and `ALL_LOCAL` the gateway reads (`sf-profile` and `sf-all-local`, beside `sf-events`): a visitor needs the bounds as much as Martin does, and they are no secret. With neither set, it is `local`, and not. The local cluster sets `FACTORY_PROFILE=local` on it as on the gateway, and `ALL_LOCAL` goes on it whenever it goes on the gateway. It writes the app's origin too, from `APP_URL` (`sf-app`), which a flag's "Preview it" opens; the local cluster sets `APP_URL=http://website.localhost:8080`, the app as a browser on the Mac reaches it.

Each is a route the access table ([`policy/access.ts`](../../policy/access.ts)) gives the console, which it answers through the table and nothing else: the table is the one list of every route and every action Martin can take, with the role each needs, whether it writes, and whether it needs his passkey again. A test fails when the server answers a route the table does not give it.

Every response carries a strict Content Security Policy (the page's own scripts, styles, fonts and pictures, and connections to its own origin, nothing inline), opener, embedder and resource policies that keep other origins' pages and resources away from it, and a permissions policy that gives away no camera, microphone, location, payment or USB.

## Signing in

Martin's side of the console is the [admin service](ADMIN-SERVICE.md)'s, on the same origin under `/admin/`. The console's server never holds a session or sees the cookie that names one; the page asks the service.

- **Who is looking.** As it opens, the page asks `GET /admin/session`: a session is Martin's, which puts his account button in the header; the service's own refusal is a visitor's, whose footer offers a key to Martin's sign-in; anything else (the replay site, `pnpm dev` with no service, a deployment without one) is no service, and offers no sign-in. When the session's hour is up, the page sends him to the sign-in page, which says so.
- **The doors.** Signing in (`/?view=sign-in`) and enrolling a passkey (`/?view=enrol`) are pages of their own, as the design system draws them, whose code and passkey ceremonies ([SimpleWebAuthn](https://simplewebauthn.dev)'s browser half) load only there. Each ceremony asks the service for its options, has the browser's own passkey sheet answer, and sends the answer back.
- **Which events.** The page draws everything from one projection of whichever events it reads, and the projection cannot tell which. A visitor's page reads the public events from the console's server. Martin's reads the full events from the service's `GET /admin/events/stream`: it opens the public ones at once, as anyone's page does, so a visitor waits on no question to the service, and once the service says the session is his and the public stream has said what kind of store it is (which only it says), the full events take over from the public ones as they arrive, each in its public view's place by seq. When the stream ends, or is refused, the page asks the service again: a session that has ended goes back to the public events and to the sign-in page, saying why; one still live, or a service that cannot be asked, opens the stream again.
- **A visitor's report** is quoted on its sheet for Martin alone, under the line everyone reads, marked "Only you see this: a visitor wrote it", and a planner's finding the same way, marked as the planner's. Only the full events carry their text, and the page shows it as spec 5.3 says, by `reportText` (`web/src/projection/report.ts`): at most 140 characters of plain ASCII letters, digits and basic punctuation, with links, email addresses and long numbers removed, inserted as text and never as markup.
- **Preview as visitor,** in the account menu, on the console and the settings alike, shows Martin the console as anyone without his session gets it: a green banner, "VISITOR VIEW" in his account's place, and everything below drawn from the public events, read afresh from the console's server rather than the full ones with his parts hidden. The full stream closes while it lasts. **Back to admin** reads the full events again; so does a reload, which ends a preview.
- **The account menu** says when Martin signed in and when the session ends, offers Preview as visitor, leads to the settings, links to this deployment's Grafana and Argo CD in a new tab when the admin service names them in his session (`GRAFANA_URL` and `ARGOCD_URL` on the [admin service](ADMIN-SERVICE.md#settings), so a public deployment's internal hosts never reach a visitor's page), holds the theme and motion switches, which a visitor has in the header, and signs out here or everywhere.
- **Writes** are `POST`s of JSON with the session's token in `X-CSRF-Token`, the one the service gave with the session (`write` in `admin.ts`). A write the service refuses for want of the passkey given again opens the step-up dialog, and is sent again once it is given.
- **The passkey, again.** An action the access table marks carries a key after its label while the passkey is not fresh (which actions, and for how long, are copied from `policy/access.ts` into `web/src/access.ts`, since the image is built without it, and a test holds them together). Pressing one opens "Your passkey, again" (`StepUp.tsx`): the action's name, what will happen in a ruled box, why it asks, and **Use your passkey**, which runs the service's step-up ceremony. Once given, the header shows "Passkey given · 5min", counting down, the keys go, and on a phone the count is in the account menu instead. The pill is a button: pressing it ends the five minutes there and then (`POST /admin/step-up/end`, which asks for no passkey, as it only tightens), the pill goes, and the keys are back, so the next action that asks asks again. The page's count is a convenience: the service decides.
- **Dialogs** (`Dialog.tsx`) are the browser's own modal `<dialog>`: a raised card on the scrim, a bottom sheet on a phone, its title focused as it opens, and the control that opened it focused again as it closes; Escape, the scrim or Cancel close it. A screenshot at full size uses the same dialog, wider (`ShotViewer.tsx`).
- **Read only.** Everyone but Martin sees each of his controls as a label (`.ro`) beside what it does, never a greyed-out button.
- **In development,** `pnpm dev` passes `/admin/` to an admin service on the host when `ADMIN_URL` names one, and keeps `Cookie` from the console's server as Traefik does, started with `ADMIN_ORIGIN=http://localhost:5173`: `localhost` is a secure context, so a passkey and the `Secure` cookie work there in Chrome; Safari drops the cookie over plain HTTP.

Every browser test fails on a request to another origin, on a Content Security Policy violation, and on anything left on the device but `__Host-session`: a cookie, local or session storage, IndexedDB, Cache Storage or a service worker (`e2e/support.ts`), in every context and page it opened, popups among them, that is still open when it ends. `privacy.spec.ts` holds the guard to that: it fails a test that leaves something in a popup or a context of its own. `privacy.spec.ts` opens each view as a visitor, changes the theme and motion, and finds nothing kept at all; signing in finds `__Host-session` alone, and signing out nothing. The app's preview cookie is not on that list: the console sets none of its own, and a link to the app is to another origin, which no test follows.

The browser tests take the doors, Martin's view, the Canary panel's controls and a canary paused for Martin (against a stand-in Rollout), Stop the line, Start the line and the line's controls, and the "+" and approving an improvement's spec, through the real service and the console's server, both on a throwaway store holding the samples (each visitor's report with a text, as its full event carries one), behind a proxy standing in for Traefik, with a virtual passkey; ZAP's baseline scan runs against the same in CI, signed in that way ([CI pipeline](CI-PIPELINE.md#zaps-baseline-scan)).

## The browser

- **It projects.** `project(events, t)` is plain TypeScript, so live and replay are the same code.
- **Replay.** The same build, fed from an event-log folder, is the replay site.

## What the image holds

Neither the factory's code nor the app's repository.

- What the projection shares with the line (its limits, how a scope matches a path, a return's words) is in `@software-factory/events`, which both read.
- The bounds of Martin's settings and the one check of them (`policy/models.ts`, `policy/spend.ts`, `policy/settings.ts`), which the page shares with the gateway, the line and the admin service, so all four agree on what is in force; the bounds of the line's controls and their check (`policy/line.ts`), which it shares with the line and the admin service; the feature flags' stages and the rules of moving one (`policy/flags.ts`, `policy/flag-moves.ts`), which it shares with the admin service, so a stop it draws as one that can't be taken is refused in the same words; and the profiles (`policy/spend.ts`) for the server.
- A spend hold carries its cap.
- The app's reviewing rules are the one copy it keeps.
