# Patching

How the factory keeps what both repositories run and pin patched: the scan's moves, and the dependency sense that reads them each day. Part of the [factory plane](README.md#factory-plane); [the patching diagram](../architecture/patching.html) follows one from advisory to cluster. A **move** is one thing (a package, an image, Node, a chart, k3s) going from what is pinned to a target, in one repository, with every pin that names it: the unit of work, as a finding, one package and one advisory in one item, is the unit of evidence ([terms](../TERMS.md)).

## The moves

The daily [vulnerability scan](SECURITY-SCANNING.md) groups each day's findings with a fix into moves, a pure function of its results (`apps/factory/src/vulnerabilities/moves.ts`), each with its pins, from and to, what it clears and leaves by severity, its earliest deadline, how many of its findings are new today, and its lane, which says who moves it. It uploads them as `moves.json`, with every image it read (`scanned`), and each result's message names what fixes it and its move. The factory reads them only through the [GitHub worker's `moves` read](GITHUB-WORKER.md#for-patching), which checks the artifact against the state the scan sealed, and the review gate reads the same two artifacts for itself ([a move](APPROVAL-ROUTING.md#a-move)).

## The dependency sense

`factory patching` (`apps/factory/src/patching`), a worker of its own in `factory`, connecting to the store as its own role, `factory_patching`. As it starts, and each day at 05:30 UTC once the scan (04:17) has finished (`PATCHING_AT`), it:

- asks the GitHub worker, through [its door](GITHUB-WORKER.md#the-senses-door), for both repositories' moves;
- lists the images every pod runs (its init and ephemeral containers too: an image `kubectl debug` runs is one the cluster runs), by the reference its spec names and the digest its runtime resolved, in every namespace but three ([below](#the-namespaces-it-reads); in `PATCHING_NAMESPACES`, an empty item or a name that is not a namespace's stops the sense as it starts, since it would list every one), since an image the list lacks may run in any;
- compares the two, and appends the day as one event, `patching.read`, when it differs from the last it appended.

A read that fails, of either repository or of the cluster, appends nothing and says which failed in its log, as an error; it tries again an hour later, until the day's read comes round. A `conflict`, GitHub's own 409, is a failure like any other, the moves read's too. A pass whose failed reads were all refused at the worker's door, or that the store refused (`ECONNREFUSED`: the worker is starting, as when a deploy restarts it beside the sense, which reads first, or the network policy has not yet admitted a new pod, which has taken up to 2.5 minutes on a new cluster), appends nothing, says so as information, and is taken again fifteen seconds later; the 21st in a row, some five minutes after the first, is a failure, and a refusal of the cluster's read is a failure at once. `--once` exits 0 for a day read, 1 for a read that failed, and 75 for a pass refused; the count is the running sense's, so a `--once` refused exits 75 each time. A day that says what the last said appends nothing: a pod made again under a new name, or a Deployment scaled, is no new day while its row stands. It acts on no store of samples.

### The day

`patching.read` (`packages/events/src/schemas.ts`) holds, for each repository, the scan's run it was read from (its id, how it was started, its conclusion, commit and link), when the scan judged its moves, why it failed as its own totals count it (a finding past its deadline, one due within a day, a new High or Critical with a fix, or `other`), its totals as `moves.json` gives them, copied and never worked out here (results with a fix, the moves and the moves in each lane, and the findings with no fix, excepted, past their deadline, due within a day, and new today at High or Critical with a fix and without; and every open finding by severity, where the scan counted them, which a day read from a scan made before it did has not), how many images it read, and its moves as `moves.json` gives them, with one addition: a lockfile's move's package, versions and pins, which the scan's state gives and the artifact withholds (`package`), which the public view leaves out; everything else is as the scan's log has it. The line's issue for the move (`issue.opened`) does not change the row: a public row of a lockfile's move carries only its file, so two moves in one lockfile cannot be told apart, nor the row joined to a work item.

Only the sense's role appends it, by a restrictive policy every role's insert must meet, and Martin's command line only as samples (`0050_patching.sql`): the Patching panel, Needs you and the alerts to Martin's phone read what waits and what is due from it, so no worker that untrusted input had turned can write a day in which nothing waits.

### What the cluster runs that the list does not say

Each is a row of the day, with no target, since each means the list or the cluster is wrong (`apps/factory/src/patching/compare.ts`, a pure function of the pods and the lists):

- **`unscanned-digest`**: a container runs a reference the list has, at a digest the scan never read: a tag rebuilt upstream since the scan, or since the pod pulled it. A pod's digest may be its index's or a platform's manifest's: the list gives every one the scan saw of each image.
- **`unlisted-image`**: a container runs an image no item of either repository names, or one whose repository the list names at other references only.
- **`not-running`**: a pin `main` holds that the cluster does not run yet, while it runs another reference of the same image instead: Argo CD after a merge, a k3s move not yet applied. The pin of an image no pod runs at all is no row, since an image may run only now and then (a runner's, a Job's); nor is one of a kind no pod runs (a workflow's, a build stage's, k3d's).

A reference is compared by its repository, normalised as Docker does (`postgres` is `docker.io/library/postgres`), then by its digest when the pod names one, or else by its tag. With a repository's list missing, as when its scan failed before it wrote one, the cluster is not compared (`compared: false`), since every image of it would look unlisted.

### The namespaces it reads

Every namespace the cluster has, `default` included, but three, which `PATCHING_NAMESPACES` lists and the RoleBindings bind; a test holds the two together, and fails for a namespace `deploy/` renders, or one of the cluster's own it names (`default`, `kube-system`, `kube-public`, `kube-node-lease`, `argocd`, `kyverno`), until it is in one or named as left out. A namespace made at run time (by a chart, a try, or a k3s of another version) is in neither, and is not read until someone adds it.

- **`runners`**: an agent step's Job carries its job token in its spec, as a value (a pin step's and a lockfile's carry none), so whatever lists pods there can read live tokens; only the line may.
- **`red-team`**: only the red-team harness's two attack pods run there, each held by an admission rule to one of two images and a pinned command, the unsigned one refused as it is created.
- **`scoreboard`**: the answer key's namespace, where no role of ours is bound but the line's list of its Events, so that nothing can reach the key.

Admission control admits only images `build.yml` signed, and the third-party images it names by digest, in all three (ADR 0010), so an image the list does not have cannot run there. What cannot be seen there is the first row: an older signed image of ours still running, a digest no result names, which admission does not stop.

### Its fences

- **The GitHub worker's reads, and no action.** The worker's main port acts in GitHub, so the sense asks its own door, on a port of its own (8083), which serves `moves` and nothing else; a NetworkPolicy opens it to the sense's pod alone.
- **Pods, listed, and nothing else.** Its account's one right is a ClusterRole, `patching-lists-pods`: list pods, never get, watch or anything else, bound by a RoleBinding in each namespace it reads and by no ClusterRoleBinding (`deploy/base/patching-reads-pods`).
- **Its own role.** `factory_patching` appends `patching.read` and nothing else, reads only its own events, and no other table; it is no member of `factory_worker`. Its password is in `postgres-patching`, which `make up` makes and the migrate Job sets.
- **Its NetworkPolicy** gives it the store, the collector, the API server on 6443 and the worker's door, and takes nothing in.

On the host, `factory patching --once` makes one pass against the cluster's GitHub worker and says what it appended, or why not: [on the host](../ON-THE-HOST.md#the-dependency-sense) has the commands.

## The pin watch

This repository's moves are the GitHub worker's to make ([its pin watch](GITHUB-WORKER.md#pins)), from the same moves read, which the worker keeps, so the watch's hourly pass and the sense's daily one download the run's artifacts again only for a new scan run, or once one of them has expired. Every move in the `worker` and `cluster` lanes is in a pull request of the App's, one for the day's moves at a set of files, with a major apart, which changes nothing but what those moves write, as [its guard](GITHUB-WORKER.md#the-pin-guard) holds it: the version or digest at each pin, or, for a move no pin's line writes (a lockfile's package, what mise pins, an image that brings its Node or its library), the files the scan's own run made with the pin step, committed whole ([the moves the scan makes](SECURITY-SCANNING.md#moves)). A move in the `issue` lane, a line no longer built, one whose pins' lines it cannot write and one the pin step refused is an issue. The App makes every move the scan lists: a pull request of Dependabot's for the same pin is left as it is, and Dependabot closes it itself once `main` has the version. The review gate passes the App's pull request as `move` when it is exactly the scan's moves, which the gate makes itself on `main`, or as `major` when one of them crosses a major and clears no Critical by Trivy's own rating ([a move](APPROVAL-ROUTING.md#a-move)); the worker adds it to the merge queue when the autonomy level and auto-merge queue that rule ([the worker's part](APPROVAL-ROUTING.md#the-workers-part)). k3s's pull request merges as any other, and reaches the cluster when Martin runs `make upgrade-cluster`, as its description says. It takes only the moves its deployment names in `PIN_WATCH_ONLY` (or every one, `*`), and none while none is named. The app's moves are its line's.

## What it sends triage

Every pass that reads, the day changed or not, the sense sends each of the app's moves in the lane `line` that has a target to triage's inbox, as a `dependency` signal ([a move](TRIAGE.md#a-move)): the move as the signal names it, and the scan's findings, worst first, at most eight, with the rest and what the move leaves on its pins counted. A move with no target, or in any other lane, sends nothing. A lockfile's move is sent by its package, which the read takes from the scan's state, in the `npm` ecosystem, and a package locked at two versions under one advisory as one move from both; an image's is `docker`, Node's own binary `node`. Only the fixed fields the state holds of a finding are sent, each checked against the signal's shape; a finding that does not fit is counted with the rest. A finding says of its advisory only what the state says: its id, its package, its rating and the versions that fix it (`fixed in …`), each once and lowest first, absent for `no fix yet`; versions that do not fit the signal's shape are left out, and the finding sent without them. The move's target is the move's `to`, never a finding's: an image moves to its tag, and its packages are fixed in their own versions.

**A move that needs another Node** is sent as a move of Node, from one release to another, which the pin step writes whole (`mise.toml`, `mise.lock` and each `FROM` of a Node image): Node's own fix found in the build stage's image, which a tag that names its release pins; and that image moving to a tag of another release, whose `FROM` written alone would leave mise's pin behind. The same tag built again is the image's own move. Node's own fix found in the runtime's image, whose tag names no release, is that image's publisher's to bring: it is said and not sent. A move of an image brings what goes with it: the pin step reads the Node the image runs at the move's digest and, where it is another release than `mise.toml` pins, moves Node with it, and Playwright's image brings its library in the lockfile (`apps/runner/src/pins.ts`); the scan gives such a move no deadline until that Node is one mise may install ([deadlines](SECURITY-SCANNING.md#deadlines)).

**The same send** is one move of one repository from one run of the scan, and has one id, derived from those three: a sense restarted on the same day sends each again under the same id, and the inbox keeps the first. Triage says it too, since the inbox prunes counted signals after three days: a signal that says what its ticket's last said is counted and appends nothing. A new run is a new send, counted on the ticket, or joining it when its target or findings changed.

Its role may send only its own sense's signals and reads none of the inbox (`0051_patching-sends.sql`). A send that fails fails the pass, the day appended, and the next pass sends again.

## Trying a move before a push

Two things carry a move the whole way on the Mac, with nothing pushed, so a move that cannot pass is found before it is a pull request.

- **The app's moves:** `apps/factory/test/patching/path.test.ts` carries a scan's finding through the real code of every step (the scan's judgement and moves, the sealed state, the worker's read, the sense's signal, the pin step on a copy of the app's pins, the worker's guard and the review gate's tags), one case for each kind of move the scan can make of the app. A case with a `gap` is a move the scan sends the line that the line cannot make, and says what stops it.
- **This repository's moves:** `node scripts/rehearse-pin-moves.ts --moves <moves.json>` runs the pin watch itself on a day's moves, in a repository of its own, and gives a row for each pull request it would open and each move it would not make, with the files it changes and which of the unit and database tests fail on it that pass on the base; `--compare` says whether each is the tree of origin's branch of the same name, and `--branches` rehearses the pin branches origin has. It reads `moves.json` alone, never the scan's sealed `pins`, so a move the scan's pin step makes (a lockfile's, mise's, an image that brings its Node) is a row of a move it does not make. The review gate's verdict is not rehearsed: the gate makes each move with the watch's own edit, so a move the watch makes from a day's `moves.json` is that day's `move`. A day's `moves.json` is the scan's artifact, or a local judgement's: `scan.ts <checkout> --out <dir>` then `deadlines.ts <dir> --checkout <checkout> --prove`, which upload nothing.
