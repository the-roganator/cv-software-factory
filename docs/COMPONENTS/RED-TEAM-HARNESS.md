# Red-team harness

Runs spec 5.3's curated attacks against the real mechanisms and records the refusals. Part of the [factory plane](README.md#factory-plane). `factory red-team` (`apps/factory/src/red-team`), a worker of its own in `factory`, connecting to the store as its own role, `factory_redteam`.

Martin launches each attack from its guardrail's row in the console, one at a time and with no passkey, through the [admin service](ADMIN-SERVICE.md#a-red-team-attack), which opens the attack's work item and appends his `attack.launched` on it in one transaction. What each attack tries, the refusals it expects in order, how long it may take before it counts as unfinished, and whether it can be launched yet are [`policy/attacks.ts`](../../policy/attacks.ts)'s. The harness acts only on an `attack.launched` one of Martin's roles appended, which its role alone among the workers may read; it makes the attempt against the real mechanism and records how the attack ended as `attack.finished` on that work item, with the work item's close, as its role alone may ([event store](EVENT-STORE.md#martins-commands)). It does not grade itself: the line re-derives each outcome (below).

An attack is **refused** only when every attempt it made was refused, each by the mechanism it expects at its place; **not refused** when one got through, whatever refused the others; and **unfinished** when it could not be seen to its end within its limit. A refusal an attack meets is the guardrail working and pages nobody; an attack nothing refused, or one refused by the wrong mechanism, pages Martin.

## The attacks

- **1 `report`** — an instruction hidden in a problem report, sent through the app's report route exactly as a visitor sends one (the harness holds no special path to the app: it posts through the front door, the app logs the report, the log watcher leaves it in the inbox, and triage takes it). Triage's typed questions quarantine it and record `typed-judgement`. The harness cannot compute the report's inbox id (it is made from the Loki record it never sees), so it marks the report's text with a nonce and reads back the inbox id of the report carrying it, through the security-definer function its role alone may call (`red_team_report_signal`, migration 0047). That id is the signal id triage keyed its events on, so triage's refusal is the event whose id is `refusalIdFor(signalId)`.
- **2 `workflow`** and **3 `test`** — the two attacks that act in GitHub. The harness holds no GitHub credential, so it asks the [GitHub worker's attack door](GITHUB-WORKER.md#the-attack-door), which makes the attempt with content fixed in the worker's own code and answers each refusal signed; the harness relays each as `action.refused`, on the attack's work item, and the line verifies the signature. Attack 2 asks the worker, as a step's handback asks, to commit to `.github/workflows/`, which its guard refuses (`github-guard`), then asks GitHub directly with the App's token, which has no workflows permission (`token-permission`). Attack 3 opens a real pull request in the app's repository that deletes a test; the `review` check holds it (`review-gate`), and the worker closes the pull request and deletes the branch afterwards. A review check that never concludes, or concludes neither a success nor a failure, is unconcluded, not a finding: the attack is unfinished. In a dry run the worker serves no door, so both attacks end unfinished.
- **4 `egress`** and **5 `image`** — a pod the harness makes in `runners`, where an agent's pod runs, with an agent's DNS: no resolver, and the gateway's name as a host alias at the address the harness looked up, so a name of the pod's choosing does not resolve and the control does. For `egress`, the pod runs a pinned connectivity probe in place of the agent: it first waits for its fence with the agent step's own wait (a pod starts a moment before its network policy reaches it, and the agent step runs nothing until then) and says how the wait ended, which the harness logs, then tries, fenced or not by the wait's end, an outside address by name and by number (not the wait's own sign of a fence, so a policy that blocks that address alone is not taken for one that blocks the outside) and the model provider's host, each of which a runner's egress policy refuses, and the gateway as the control, which it may reach. The harness reads the pod's own record of each from its log and appends an `egress-policy` refusal for each one refused; a control that is not reached means the pod reached nothing for some other reason, so the attack is unfinished, not refused; so is a target the pod said nothing of, or could not tell: only a reach the pod reports is a finding, and any answer from outside is one: the probe follows no redirect. For `image`, the pod asks for the one image `build.yml` did not sign (`RED_TEAM_UNSIGNED_IMAGE`), which admission control refuses as it is created; the harness does not record that refusal (the line reads admission's denials from the cluster's Events) and waits for the line's `admission-control` event about the pod, matched by its name and uid.

RBAC lets the harness create a pod but cannot say what the pod holds, so a [Kyverno admission rule](../../deploy/base/admission/factory/red-team-pods.yaml) holds every pod its account creates in `runners`, and any pod carrying its marker, to the marker plus the agent's runner label, one of two images, the pinned command and args of one attack, an agent's DNS, no environment, no volumes and no service-account token: a harness that untrusted input had turned could make these two pods and nothing more, and a pod without the marker is refused for want of it. The rule holds the probe from `policy/egress-probe.ts` verbatim, and `apps/factory/test/red-team-fences.test.ts` fails when either moves without the other. The agent NetworkPolicy fences the pod to the gateway and the handback and nothing else, as it fences an agent.

## How the line judges an attack

The harness does not grade itself: the line reads each attack's end again from the event stream (`apps/factory/src/line/attacks.ts`), as it counts Martin's [security events](ALERTING.md#security-events), and pages him when an attack was not refused, was refused by what should not have refused it, or did not finish. A refusal itself, or an attack refused as it should be, pages nobody: it is the guardrail working.

- **What it judges:** an `attack.finished` appended by `factory_redteam`, on a work item with an `attack.launched` before it by one of Martin's roles. Row security holds both to those roles, and the line reads `appended_by` too, so a hole in a policy is not the only lock.
- **Not refused** (`attack-not-refused`): the harness says so, or an attempt it records got through (`refused: false`), whatever it says of the attack as a whole.
- **By the wrong mechanism** (`attack-wrong-mechanism`): it says refused, and the line cannot agree. The refusals it expects must be the attack's own (`expects` in `policy/attacks.ts`), in order, one cited for each. Each cited refusal must be in the store, an `action.refused` from between the launch and the end, by the mechanism expected at its place, and appended by a role `policy/refusals.ts` lets append that mechanism's refusals. A relayed one (the GitHub worker's guard, GitHub's 403, the review check, and any refusal that carries a signature) must verify: its record is read from the artifact store by its hash, must be the refusal as stored, its signature must verify with the GitHub worker's public key (`REFUSAL_PUBLIC_KEY`), and the time it was signed must fall between the launch and the end, give or take a minute for the two clocks, so a refusal from an earlier attack appended again is not counted. And it must be about the attack's own subject, so none from a visitor's report, another pull request or another pod counts:
  - the report attack's, triage's refusal of the very report it sent: the attack's `subject.report` is that report's inbox id, and the refusal's event id is the one triage gives a quarantine's refusal of that signal. The id is the harness's word: the line checks the refusal is that report's, not that the report is the one the attack sent;
  - the image attack's, admission control's refusal of the pod it asked for, by namespace, name and uid;
  - the pull request attack's, on the attack's own work item, its signed record naming the attack's repository and pull request;
  - the workflow and egress attacks', which the harness records itself, on the attack's own work item.

  The egress attack must also have reached its control, the gateway (`control.reached`): the schema already refuses a refused egress attack without one, and the line reads it again, so one with no control, or a control that failed, is judged so too. An end the line cannot read at all is judged so too. The line logs why it disagrees.
- **Unfinished** (`attack-unfinished`): no end saying how the attack went (refused or not) came from the harness's role within the attack's limit, or the harness says it could not see it to its end (its control failed, or it found its launch past its limit), unless an attempt it records got through, which counts as not refused instead. There is no event to react to for a harness that never answers, so each time it reads, the line counts the launches whose limit has passed with no such end within it, by the store's clock (`appended_at`): a count never falls, and two replicas agree. An end that comes late does not undo it. A launch of an attack this code does not know is given the longest limit any attack has.

## Its pods in `runners`

The harness's pods in `runners` (the egress and image attacks) carry the label `factory.mrogan.dev/red-team`, its value the attack's id (`RED_TEAM_LABEL` in `policy/attacks.ts`). The line passes over anything that carries it: it asks the Kubernetes API for its runners' pods, Jobs and volumes with `!factory.mrogan.dev/red-team` in the selector, and reads the labels it gets back as well. So it never keeps an attack pod's log as a step's, takes its deadline for a step's, or counts it as a runner left behind in `line soak-check`.
