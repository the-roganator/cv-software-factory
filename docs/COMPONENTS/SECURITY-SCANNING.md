# Security scanning

Code, dependencies, images and secrets. Part of the [GitHub plane](README.md#github-plane).

- **v1:** CodeQL, Dependabot, GitHub secret scanning, the dependency graph of every package each lockfile resolves, the daily scan of everything either repository runs or pins, the lockfile gate on both repositories' pull requests, and two more gates on the app's.
- **Later:** Semgrep, licence checks.

## CodeQL

`codeql.yml` analyses the TypeScript and the workflows, with the `security-and-quality` queries, on every pull request, `main` and once a week, in both public repositories: the app's calls it. Each repository's `main` ruleset holds a pull request while its own analysis finds a new security alert of medium severity or higher, or a new error ([repositories and rulesets](REPOSITORIES-AND-RULESETS.md#the-ruleset)). A false positive is dismissed in code scanning, with a written reason. CodeQL does not run in the merge queue, which does not wait for it.

## The lockfile gate

`lockfile scan` (`apps/factory/src/gates/lockfile-scan.ts`) runs on every pull request and in the merge queue, in both repositories: `check.yml` here, and `app-gates.yml` in the app's gates. It fails on any vulnerability, at any severity, that the change's lockfiles have and the base's do not.

- **What it reads:** every `pnpm-lock.yaml` and branch lockfile (`pnpm-lock.<name>.yaml`, which pnpm reads or merges) git tracks, at any depth and fixtures included, of the base and of the change: whatever points pnpm at a lockfile (`lockfileDir`, a flag, a variable), the one a frozen install reads is tracked, so it is read. Each YAML document in it is scanned alone by Trivy from a directory holding only it, since pnpm reads a lockfile's later document where Trivy reads only its first; pnpm's env lockfile, the document that pins pnpm itself and its config dependencies, has those named as dependencies so Trivy reads them as production's. Each is development dependencies included, both against one advisory database pulled once from GHCR, as the daily scan's is. A lockfile the same on both sides is scanned once; one only the change has is compared with none.
- **What is new:** a vulnerability is known by its lockfile, its advisory, its package, and whether a production dependency reaches it (Trivy's `Dev`). A package moved to another version with the same advisory brings nothing new; one a production dependency newly reaches does; one the base reaches from production and the change only from development is less reached, not new.
- **It fails on what it cannot read:** a lockfile, or a document of one, Trivy reads no packages from, on either side, unless it holds nothing but its `lockfileVersion`; a document where Trivy did not read every package it lists under `packages:`, which pnpm installs whatever other sections say, or that is not written plainly enough to list them (flow style, quoted or merged keys at the top level); one whose report is empty or cannot be parsed; and a `pnpm-lock.yaml` git tracks as a symbolic link or a submodule, which pnpm would follow.
- **Judged by code the change cannot alter:** the script, Trivy's pin and the base's lockfiles come from the base (`pull_request.base.sha`, or the merge group's base) here, and from this repository at the pinned commit in the app's gates; only the change's lockfiles come from the change, as data, and nothing in either checkout runs. Here, a base with no gate and a change that brings it in, the gate's own first landing, judges nothing and says so in a notice; a base with no gate otherwise fails. The job is read-only. In the app's gates it refuses any event but `pull_request` and `merge_group`, and is skipped with the rest for the App's deploy and release pull requests.
- **Exceptions:** an entry in force in `policy/vulnerabilities.ts` on this repository's `main`, for the repository, the lockfile, the package and the advisory, excepts that finding, which the summary names and which fails nothing, so a fix whose release also brings in an excepted finding is not held by it ([exceptions](#exceptions)). The workflow puts `main`'s file in place of the one beside the script before it runs; nothing is read from the change that could except anything.

The summary names each finding the change brings in, its package, version, advisory, severity and whether production reaches it: the change is public and has not merged.

## On the app's pull requests

Besides the lockfile gate:

- **Dependency review** (GitHub's) fails a dependency with a known vulnerability the change brings in.
- **Trivy** (pinned by digest) scans the base's image and the change's, and fails on a high or critical vulnerability only the change's has.

## The dependency graph

GitHub's dependency graph, and so Dependabot's alerts, read a repository's manifests, which name its direct dependencies alone. `dependency-graph.yml` submits the rest: on each push to `main`, a snapshot of every package each lockfile on the repository's list resolves, indirect ones included, to the dependency submission API, and the app calls it (`workflow_call`) at a pinned commit, on a push alone, for its own.

- **Nothing of the repository runs.** Its checkout keeps no credentials, and each lockfile alone is copied into an empty directory, which Syft's image reads, by digest, from its one pin (`deploy/images/syft/Dockerfile`, at the version `build.yml` attests SBOMs with), read-only and with no network, for its `github-json` snapshot. Nothing is installed. The script (`graph.ts`) comes from this repository at the workflow's own commit.
- **Direct and indirect, runtime and development, and what each depends on,** are the lockfile's: Syft marks every package direct and at runtime, and gives as a package's dependencies the packages that depend on it, so the script sets a package direct when an importer names it, at runtime when an importer's dependencies or optional dependencies reach it, and depending on what its entry in the lockfile names. pnpm itself, which the lockfile also resolves, is a direct development dependency.
- **One snapshot replaces the last:** each names the commit, the ref and the correlator `dependency-graph.yml`, from a job whose token has `contents: write` alone and which refuses any event but a push to the default branch.
- **A change to it proves itself** on its own pull request, as the scan does: the same snapshot of the base's checkout, in a job with `contents: read` alone, that submits nothing, installs each lockfile as the scan's coverage does, and fails if the snapshot lacks a package `pnpm list --depth Infinity` names, calls one direct or indirect where pnpm lists it the other way, or names no indirect package. Its log gives both counts.
- **Dependency review** compares a pull request's manifests with the base's graph, so it sees a submitted indirect package on the base's side alone: it can find one removed, never added. What a change adds to a lockfile is the lockfile scan's to judge.

## The daily scan

`vulnerabilities.yml` scans everything a repository runs or pins, every day (04:17 UTC), on each push to `main` and by hand, and another repository can call it (`workflow_call`) at a pinned commit, to scan its own. Each finding is an alert in the code scanning of the repository that owns it, at the line that pins it, in one of the categories `vulnerabilities/01` to `vulnerabilities/20`.

- **What is scanned** is the repository's list (`apps/factory/src/vulnerabilities/inventory.ts`): each lockfile, on its own, development dependencies included; each image of ours, from the SPDX SBOM of each platform `build.yml` attested, verified with `cosign verify-attestation` against its signer, and from the image itself when Trivy reads no Node from its SBOM; every other image by pulling it, from CI's copy where there is one; each chart's images, from what `helm template` renders of it with the values it is installed with; and the images k3s's release lists. A pin the list does not read (`--unlisted`) is an item the scan cannot read.
- **Node itself:** Trivy reads no Node runtime, from an image or from Syft's SBOM, which names it `pkg:generic/node`. So the scan reads each image's Node version, from that package, or from the image: its `NODE_VERSION` (as Node's official images set it) or an operating system's `nodejs` package (as Playwright's image installs it), and matches it against Node's own core vulnerability database (`node.ts`: nodejs/security-wg's `vuln/core/index.json`, fetched on each run from its default branch, retried, and refused as Trivy's is when it cannot be fetched or read). Each CVE is a result of its own at the image's pin, at the publisher's severity. An image of ours whose Node version cannot be read is an item the scan cannot read. Node's match covers each image of ours, and each other image that names its Node in `NODE_VERSION` or installs it as an operating system's package; a third-party image that bundles Node another way is read without Node's own advisories.
- **With what:** Trivy, by its digest, from its one pin (`deploy/images/trivy/Dockerfile`), and an advisory database pulled from GHCR, with retries, and refused when it was built more than a day ago; Node's own database beside it, as above. The scripts, and the pins of the tools they run (`kustomize`, `yq`, `helm`, `cosign`, from `mise.lock`), come from this repository at the workflow's own commit; the scanned checkout is data. A change to that pin passes `check.yml` only when the image is signed by Aqua's release workflow on the tag of the version pinned, named whole (`https://github.com/aquasecurity/trivy/.github/workflows/reusable-release.yaml@refs/tags/v<version>`, with GitHub's OIDC issuer), as ADR 0010 holds ours. A pin of Syft's image is held by its digest and its review alone until Anchore signs its image, which is looked for again at each bump, as the check's notice in its log says.
- **Coverage first.** The `coverage` job installs each lockfile with the pnpm the scanned repository's `mise.lock` names, installed by this repository's mise, `--frozen-lockfile --ignore-scripts --ignore-pnpmfile` and no `.npmrc` of the checkout's, and fails when `pnpm list --recursive --depth Infinity` names a package Trivy's SBOM of the lockfile alone does not, so the scan reads every package `pnpm list` gives. The scan needs it to pass.
- **Where results go:** one SARIF file (`sarif.ts`), a rule for each advisory and a result for each package and advisory in each item. Code scanning keeps only the 5,000 most severe results of a run, so the file is 20 runs, each a category of its own, `vulnerabilities/01` to `vulnerabilities/20`: whole items fill them in the list's order, each run to 5,000 results; an item over 5,000 is cut, its results in order of package and advisory, into full runs of its own, and whole items fill the run its last cut begins; and the runs nothing needs are empty. All 20 are uploaded every time, because a category that stopped being uploaded would keep its last results open for good. The log names each run's items (`vulnerabilities/02: 5000 results, 1 item: .devcontainer/Dockerfile mcr.microsoft.com/devcontainers/base (cut 1 of 2)`). As the counts before it change, a result can move to the next run or the one before; its alert stays the same alert, open while any configuration reports it, and the run it left, uploaded too, no longer does. An image's copy of a package is its own result, never a lockfile's, and an image's two platforms are one result. A result's fingerprint is its item, its package and its advisory, and so is its `primaryLocationLineHash`, which `upload-sarif` would otherwise hash from the pinned line's text, digest and all: so moving a pin that leaves the finding keeps its alert, and moving it past the fix closes it.
- **A run that cannot read an item fails and uploads nothing:** a lockfile Trivy reads no packages from, an SBOM with no verified attestation, an image that cannot be pulled, a chart that does not render, or results past code scanning's limits for one upload: more than 20 runs. No alert closes because its item went unread. The log names each such item, and gives the findings by severity, never a package or an advisory. Past that, a finding fails the run only by its [deadline](#deadlines).
- **It proves it can see.** Each run also scans an image of ours from before Node 24.22.1 (`proof.ts`), as it scans ours, uploads nothing for it, and fails unless CVE-2026-111497 is found in its Node, 24.22.0.
- **Exceptions hold the alerts.** After the upload, once code scanning has processed it, the scan dismisses as won't fix the alert of each result an exception in force excepts, its comment the entry's reason and expiry, and reopens every alert of its own categories (`vulnerabilities/01` to `vulnerabilities/20`, never CodeQL's or Scorecard's) dismissed with no exception in force, by anyone (`alerts.ts`). So those categories' state is the policy's and nothing else's: a finding is closed only by its fix, or excepted only by an entry on `main`. An excepted finding is still uploaded, its alert dismissed rather than gone. The log counts the entries, those in force, the results they except, and each change it made by alert number; it names each entry that excepts nothing, to be removed, and warns, failing nothing, when the repository's `osv-scanner.toml` is not the one the policy gives it.
- **A change to the scan proves itself** on its own pull request: the same scan of the base's checkout, in a job with no permission to write, that fails as the real one would and uploads nothing. It reads the repository's alerts (`security-events: read`) to give the deadlines' counts and the moves, fails on none of them, and uploads its `moves.json` as the real run does; its log's last lines name the moves that hold whatever the real run would fail on. Its first step refuses a pull request from a fork, whose token would read the repository's alerts, which are not public, so a change to the scan from a fork is proved from a branch of this repository. A fork supplies its own copy of the workflow, so the step binds only a fork that leaves it in place; what binds one that removes it is the repository's approval of fork runs, which a fork cannot change. Every job that writes refuses any event but a push to the default branch, the schedule or a run by hand there.

## Deadlines

Before the upload, the scan finds what fixes each finding and gives each open finding a deadline (`deadlines.ts`), worked out afresh on every run from what it read, the registries and code scanning, with no state of its own but what the alerts hold.

| Severity | Days from the clock's start |
| --- | --- |
| Critical | 2 |
| High | 7 |
| Medium | 30 |
| Low | 90 |

- **Severity** is the higher of Trivy's and the publisher's: Trivy's `VendorSeverity` for the advisory's own source (GitHub's advisory for an npm package, the distribution's for an operating system's); Node's own findings take the `severity` of their entry in Node's core vulnerability database. A finding neither rates takes Low's days.
- **The fix is installable**, for an npm package of ours (a lockfile's, or one in an image of ours that a lockfile of ours resolves at that version), from the first fixed version's publish time in npm's registry plus the scanned repository's `minimumReleaseAge`, or pnpm's default of a day; for Node, from the first patched release in Node's release index; for anything else in an image, from the creation of the newest image on the line of the pin that brings it (the runtime stage of its Dockerfile, for an image of ours), the tag `scripts/ci-images.sh`'s `newest` would find, or the tag's current image for a tag that is not a version, once that image no longer has the finding. An image that arrives only with a k3s release (metrics-server, CoreDNS, klipper-lb, Traefik: those its `k3s-images.txt` lists) is installable from the publication of the first k3s release after the pin, on the same Kubernetes minor, whose list carries a copy without the finding: its own newer tags are not ours to install, and another minor is an upgrade, not the fix. A node image tag with no published, stable release (a 404, a draft or a pre-release) is passed over and named in the log, and so is a repository the last release read no longer lists. The log counts these results with and without such a release. A chart's image is fixed by a chart: the newest chart on the pinned major, rendered with our values as the scan renders it, whose copy of the image lacks the finding (its four newest versions tried, newest first), installable from that chart's publication in its repository's index; when no chart on the major has it, the same on the next major, up to three majors on, marked a major. A later chart that will not render with our values is passed over, and the log names it. An image one of the chart's values files pins by digest (a value's pin: Kyverno's four, the sidecar's two, Argo Rollouts') is an image of its own, fixed on its line, as any other: its alert stays at the chart's pin, and its move writes the value's line. In an image of ours, a finding its runtime stage's image has comes with a newer one of those, an npm package a lockfile of ours resolves comes through npm, and a package a tool in `mise.toml` brings (the runner's pnpm, under `/opt/pnpm`) comes with the newest release of that tool in `mise.toml`'s range for it (its four newest tried) whose download, scanned as a file system, lacks it, installable from that release's publication; anything else its Dockerfile adds itself (corepack copied from a Node stage, say) has no fix to count from. A tag that is not a version, whose image was made more than 180 days ago and still has the finding, is a line no longer built: a move with no target, listed, with no deadline. A 404 from npm, or a tag list skopeo does not give, is a source not read. A package in more than one version is installable once every copy's fix is. Node's fix is a patched release on the major installed. Only an image with a finding Trivy says is fixed has its line's newest scanned, each once, and nothing is uploaded for it; a newest that gives no time it was made (a reproducible build says 1970) gives no day to count from, and the log warns. While no fix is installable there is no deadline.
- **The day a fix is installable never moves forward.** A tag rebuilt each week has a newer image each week, so a day read from the newest image alone would slide, and a Medium there would never come due. So the fix's day is the earlier of the day the sources give and the day the finding's own alert already states (its message's ending, below), read from code scanning before the upload: the scan keeps no state of its own, and the alert, which holds the clock's start, holds the fix's day too. Where a run finds no fix installable but the alert states one (the newest image flagged again, say), that fix stands, so a deadline once started never goes. Code scanning keeps a dismissed alert's message as the last upload wrote it (each new analysis becomes its most recent instance, dismissed or not), so an excepted finding keeps its day. A message whose ending does not parse states none, and the log counts it.
- **The clock starts** on the later of the day the fix is installable and the creation of the finding's alert, read from code scanning with the job's token; a finding with no alert before today is first seen today. Nothing done to the pin restarts it: where code scanning split a result's alert (a re-pin before the scan set its own `primaryLocationLineHash`, and once more at the first upload that does), the alert it closed in the same upload that opened the next gives its day; an alert closed by a real fix, with the place clear until the finding came back, does not. A rename keeps its clock: when an item is new to the list, and an alert of the same package and advisory belongs to an item no longer on it, the new finding takes that alert's day: a lockfile's from a lockfile's, an image's from the same image's repository. An exception does not restart the clock: its alert is dismissed, not closed, so a finding whose exception lapses returns with the deadline it always had. An excepted finding has no deadline.
- **The run fails** on a new High or Critical (first seen today) with a fix installable, on a finding due within a day, and on one past its deadline. A new High or Critical with no fix installable is counted on its own in the log and the summary, and fails nothing: a failed run always means a move exists that has not been made. The verdict is judged before the upload and the run fails on it after, so a new finding's alert exists, and its last lines name each reason with the moves that hold it. A source the deadlines cannot read (npm, Node's index, an image line's tags, its newest image or its index digest, a chart's index, a tool's releases, code scanning) fails the run before the upload, so no alert's message loses its day.
- **Counts alone.** The log and the step summary count the open results by severity, and by overdue, due within a day, within a week, later, and no fix, with the excepted and the new High or Critical; never a package or an advisory, which code scanning holds.

## What fixes it

Each result's message, which its alert's latest instance carries, ends with what fixes it and the day that was first seen installable, in one grammar (`apps/factory/src/vulnerabilities/fixes.ts`: `fixText` writes it, `readFix` reads it, the `Target` and `Fix` types are its shape): `Fixed by <target>, first seen <day>.`, the day UTC to the second (`2026-11-10T19:19:04Z`). A finding with no fix installable has no ending. The targets:

| Target | As the message writes it |
| --- | --- |
| A version, or one for each copy of a package | `version 1.0.1`, `versions 1.0.1 and 2.0.3` |
| An image's tag and index digest, as `scripts/ci-images.sh current` reads one | `image 2.14.3@sha256:<64 hex>` |
| A chart on the pinned major, or a later major | `chart grafana 13.7.0`, `chart grafana 14.3.1 (a major)` |
| A k3s release | `k3s v1.37.2+k3s1` |
| A tool's release | `tool pnpm 12.17.0` |
| A line no longer built, with no target | `another line (this one last built 2025-10-16T08:00:00Z)` |

A result in a move ends, after its fix, with its place in that run's `moves.json` (`moves`, from 1) and the run: `Move 3 of run 19234567890.` (`moveText` writes it, `readMove` reads it, the type `MoveTag`), so a reader of the alerts ties each to its move without the grouping, and tells an upload of another run from the artifact's; an index names nothing of a lockfile's hidden package. The scan reads the day back from the alert on its next run, and the GitHub worker reads each alert's ending for what `moves.json` withholds. An ending that starts `Fixed by ` and does not parse is an error to its reader, never a finding with no fix.

## Moves

A finding is evidence; a move is the unit of work. `apps/factory/src/vulnerabilities/moves.ts` groups the day's results into moves, a pure function of them (`moves`): every result with a fix on the same pin (its name, and what it pins now) is one move, wherever it is pinned, to the furthest target any of them needs (a chart's later major over its newest on the pinned major), and a line no longer built is a move apart; Node's own finding in an image moves with the image, whose newer tag brings the newer Node; and versions alone are joined, the highest on each major, so one image in three Dockerfiles is one move of three pins, and a package in two versions is one move. A chart's images are the chart's own, so two charts that run one image are two moves. A move (`Move`) has its repository, its name, every pin (file and line), from, to, whether it is a major, what it clears and what it leaves on the same pin by severity, its earliest deadline, how many of its results are new today, and its lane, which is worked out, never chosen, in this order:

| Lane | Who moves it | What |
| --- | --- | --- |
| `none` | nobody | a line no longer built |
| `line` | the app's line | the app's moves |
| `cluster` | the cluster's own command | k3s, and what its release brings |
| `issue` | Martin, from an issue | anything mise or the Makefile pins, a major or not (k3d, Argo CD's chart with its CLI, a tool's release), a workflow, an indirect package of the lockfile, a direct one Dependabot has not moved within a day of its fix, an image whose other half is in the lockfile |
| `approval` | Martin | a major, of any kind (a chart's later major, or a version past every copy's major): more than its pins' lines. Whether a chart within its major changes more than its images is the review gate's to prove from the pull request (task 33's pin move), not the scan's to assume; until the gate can, it holds such a pull request for Martin |
| `dependabot` | Dependabot | a pin its docker entries read, with no High or Critical on a deadline, and a direct package of the lockfile within a day of its fix |
| `worker` | the GitHub worker | every other pin: an image's digest, a value's pin, a chart within its major, a stage of a Dockerfile Dependabot does not read |

The log and the step summary print the table of moves (name, from, to, what it clears and leaves, new today, deadline, lane) and the totals: results with a fix, moves, and moves by lane. The same is uploaded as the artifact `moves`, `moves.json` (`MovesFile`, with `version: 1`, the `MOVES_VERSION` a reader checks, and `run`, the run that made it; its `totals` are the results with a fix, the moves and the moves by lane, and the day's counts the log prints, `DayCounts`, each taken from the verdict's own count: `noFix`, `excepted`, `overdue`, `dueWithinDay`, and the new High or Critical today with a fix to install, `newHighWithFix`, and with none, `newHighWithoutFix`), and beside the moves `scanned`: every image the scan read, whatever it found (`ScannedImage`: the item's kind and name, the image's reference, its digests, which are the index's and every platform manifest the index lists, read with skopeo, so a pod's image id of either kind is matched, and its pin's file and line), so what a cluster runs can be compared with what was scanned; it holds references from public files and no package, advisory or count, which holds nothing the log does not. A lockfile's move is "a package in `pnpm-lock.yaml`", marked `lockfile: true`, with no package, version or line, which in a public lockfile would name it; its alerts hold the rest, for those who can read code scanning.

## Exceptions

A finding that cannot reach us in the item it is found in is excepted by an entry in `policy/vulnerabilities.ts`, and nowhere else: the repository, the item (a lockfile's path, an image's reference, a chart's Application, as the repository's list names it), the advisory (a CVE or GHSA id), the package, why it cannot reach us there, and the last day it is in force.

- **One item each.** An entry matches its item alone, so the same package and advisory in another lockfile or image is still a finding. An image is named without its digest: a refresh of the same tag keeps the exception, and a new tag is a new image, judged again.
- **At most 90 days.** An entry whose expiry has passed, or is more than 90 days from the day the scan runs, excepts nothing, and the scan's log names it to be removed. An exception is renewed by a new expiry, judged again.
- **Read from `main` alone.** The scan and the lockfile gate take the file from this repository's `main`, whatever commit their caller pins, in place of the copy beside their scripts, so an exception holds only once Martin has merged it: the file is code-owned with the rest of `policy/` and imports nothing. A pull request cannot except its own finding.
- **Its test** (`apps/factory/test/vulnerabilities/exceptions.test.ts`) fails `make check` on an entry with no reason, an expiry more than 90 days away or not a day, a repository not one of the factory's, an advisory that is not a CVE or GHSA id, or an item not on that repository's list (the app's is read from its checkout beside this one, where there is one; its daily scan names such an entry in any case). An expired entry is the scan's to report, not a failure of `make check`.
- **Scorecard's view.** `node scripts/osv-scanner.ts <owner/name>` prints the `osv-scanner.toml` the policy gives a repository, an `IgnoredVulns` for each advisory excepted there, until its earliest expiry, which OSV-Scanner reads beside the lockfile for Scorecard. OSV-Scanner ignores an advisory across the repository, so the file is Scorecard's view alone; the scan and the gate match each entry to its item. This repository's is at its root, code-owned.
