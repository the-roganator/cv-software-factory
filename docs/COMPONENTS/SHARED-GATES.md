# Shared gates

One rule for both public repositories, out of the app repository's reach. Part of the [GitHub plane](README.md#github-plane).

- **v1:** reusable workflows in this repository, called from the app's repository at a pinned commit:
  - the title check;
  - CodeQL;
  - Scorecard;
  - the daily scan (`vulnerabilities.yml`), whose results reach the caller's own code scanning ([security scanning](SECURITY-SCANNING.md#the-daily-scan));
  - the app's gates (`app-gates.yml`).

The app's gates take their scripts from this repository at that commit (`apps/factory/src/gates`, Node with no dependencies and one shell script, from a sparse checkout), and Trivy's pin, and the probes and crawler from the `factory-browser` image the local profile pins. The daily scan takes its scripts and Trivy's pin from this repository at that commit too, and reads the caller's checkout as data. They see only the change's checkout and the base's, but for test integrity, which reads the pull request's description through the API for the tests its spec contradicts. The lockfile scan reads only each side's lockfiles, as data. The lockfile scan, the image scan and dependency review take their exceptions from `policy/vulnerabilities.ts` on this repository's `main`, whatever commit the app calls, and read them by one function, so the three agree on what is excepted ([on the app's pull requests](SECURITY-SCANNING.md#on-the-apps-pull-requests)): the app's call moves to a commit that has it for its image scan and dependency review to read them. The change is the pull request's merge commit, and the base, `BASE_SHA` in each job, is the commit that merge commit is made on, the base branch as it was when the run's event happened (`gates/base.sh`), not the event's `pull_request.base.sha`, which GitHub leaves where the base was when the pull request opened: a long-open pull request is not judged on what `main` changed before the event. A re-run keeps its event's merge commit; a fresh event (a push, or closing and reopening) takes `main` as it is then. In the merge queue the base is the group's, `main` with the entries ahead of it. What they check is in the [CI pipeline](CI-PIPELINE.md), [test integrity](TEST-INTEGRITY.md) and [security scanning](SECURITY-SCANNING.md), the [lockfile gate](SECURITY-SCANNING.md#the-lockfile-gate) among it. The lockfile scan and the image scan each leave a notice of what they counted by severity, which the line records from GitHub Actions' run of them for the head ([what the scans counted](SECURITY-SCANNING.md#what-the-scans-counted)): the app's call moves to a commit with them for the line to have counts.
