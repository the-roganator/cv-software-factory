# 0014: The repositories move to an organisation for the merge queue, and review becomes a gate

## Decision

Both public repositories move from Martin's account, `mrogan`, to the organisation `the-roganator`, on GitHub's Free plan, so that `main` can use GitHub's merge queue. The queue replaces the rule that a pull request be up to date with `main` before it merges.

GitHub's review rule, the `main: review` ruleset and its admin bypass (ADR 0009), goes, and a required check takes its place: `review`, posted by a GitHub App of its own, the review App, and required from that App alone, by its integration id, `5470762`. It passes when

- Martin opened the pull request from a branch in the repository, known by his account's id, `6206459`, never by his login; or
- Martin's latest verdict on the pull request approves the commit at its head: an approval given before the last push, dismissed, or followed by his asking for changes does not count, and nobody else's approval counts at all;
- the factory's App opened it, and it is an exact pin: every changed line a `digest:` value of an image `build.yml` signed on `main`, from a commit that descends from the one the pin it replaces was built from;
- the factory's App opened it in the app's repository, and it carries no risk tag; or
- the factory's App opened it in the app's repository, the app's `AUTONOMY` variable is `lights-out`, and none of its tags is a release, an improvement or a path CODEOWNERS gives Martin.

That is approval routing (spec 4.3), and the gate is its one check: [How the gate routes](#how-the-gate-routes).

The `main` ruleset, which nobody bypasses, keeps everything else: pull requests only, squash merges, signed and linear history, the required checks, now with `review` among them, and the merge queue.

### How the gate runs

- **Only `main`'s copy of the gate runs with the App's key.** `review.yml` runs on `workflow_run` alone, which runs the workflow as the default branch has it, with `main` as its ref, and its job uses the `review` environment, which holds the App's key and which only `main` may use. A workflow a pull request runs has its merge ref, `refs/pull/<number>/merge`, which the environment refuses. Nothing runs on `pull_request_target`, which GitHub's default event policy blocks in public repositories from 2 December 2026. The gate (`scripts/review-gate.ts`) reads the pull request and its reviews through the API and never checks out, builds or runs its code.
- **A pull request, or a review of it, asks for the gate.** `pull_request` and `pull_request_review` run the pull request's own copy of a workflow, with a read-only token and no secret for a fork's. So `review-requested.yml` runs when a pull request into any branch opens, moves, is reopened, made ready or edited (its base changed, as when the one below it in a stack merges and GitHub retargets it), and on a review; it holds no secret and writes nothing, and only finishes. Its run starts `review.yml` on `main` through `workflow_run`, which reads the verdict afresh and posts it on the pull request's head. Anyone who can push a branch can make a workflow of that name run, so the request says only which pull request to look at: a forged one makes the honest gate look again, and a pull request that changes `review-requested.yml` so that it asks for nothing leaves the check missing, which holds it as a failing one does.
- **A pull request into any branch is judged.** The ruleset targets `main` alone, but GitHub evaluates every pull request in a stack, into the branch of the one below it, against the rules of the stack's base, its required checks among them (GitHub's [stacked pull requests](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests) reference), so each needs a `review` check of its own. A pull request into another branch that is in no stack is required no check, and the gate judges it all the same. The rule names no base, so it is the same for all: a fork's pull request into a feature branch waits for Martin's approval of its head, as one into `main` does. A check is on a commit, so it is every open pull request's with that head: the gate judges the commit on all of them, the open pull requests here that GitHub lists for the commit with it as their head, and passes it only when each passes, naming those that do not otherwise. Every run that judges a commit, whichever of them asked, reaches the same verdict from the same reviews, so two pull requests at one commit, from different branches or with different bases, never hold it to different rules. Runs from different branches are not serialised, so one that read the reviews before Martin's approval can post after one that read them after: that failure holds the commit until the gate is asked again, and passes nothing. If the list cannot be read, the check fails, saying so; for a commit already on `main`, GitHub lists only the pull request that merged it, so the one that asked is judged alone. What reaches `main` is judged on the queue's commit, as below: on the pull request into `main` the queue names, or, for one into another branch, on it and every pull request below it; on its head, each pull request in a stack carries only its own change, which its own check covers. A pull request the gate finds open always gets a verdict, a passing or a failing check with its reason as its title, so a pull request never waits on a check that is missing for want of one.
- **The merge queue's commit gets the check too.** The queue tests each pull request on a commit of its own, on a branch `gh-readonly-queue/main/pr-<number>-…`, and every required check must pass there. Workflows that run on `merge_group` run as that commit has them, which carries the pull request's change, so the gate never runs there: `review-requested.yml` runs on `merge_group`, and `review.yml` on `main` judges the pull request the branch names, as it is now, and posts on the queue's commit. A queued stack, as queueing #665 (#657 to #660) on 27 October 2026 showed, gets an entry for each of its pull requests, each on a branch of that same name, and each built on the entry below it: the base commit in #658's branch is #657's queue commit, and so on up. So the queue's commit for a pull request into another branch carries its own change and every change below it, which its own approval does not vouch for. The gate follows its base down: the base is the head branch of the pull request below, the one open pull request here from that branch, whose base is the next, until one is into `main`. It judges every pull request on that way down by the same rule, and passes the queue's commit only when each passes. It fails the commit, saying why, when the way down breaks, when a branch is the head of more than one open pull request, when it comes back on itself, when the stack is longer than ten, or when GitHub cannot be read. A failing check takes that entry, and those above it, out of the queue, and Martin queues them again. When the pull request below has merged and GitHub has not yet retargeted the one above to `main`, no open pull request comes from its base, so a run in that moment fails; the entries are all built and asked for when the stack is queued, and the one below merges only once its checks pass, so a run lands there only if the queue builds again in the moment between the merge and the retargeting. Once retargeted, the pull request is into `main` and judged as any other. A merged pull request below is never taken as vouched for: its branch can move after it merges, and what it gains would be in no pull request's change. A queue branch the gate cannot read fails the check on the queue's commit, with the branch in its title. The environment's branch rule allows `main` alone; nothing on the queue's branches ever holds the key.
- **Every required check runs on `merge_group` too,** so the queue's commit reports each one: `check.yml` and `pr-title.yml` here, and in the app's repository its own checks and the app's gates (`app-gates.yml`), which it calls from its queue as from its pull requests. In the queue, `check.yml` runs everything but for the factory's App's deploy, which it tells there as on the pull request, by the lines the entry changes and the author of the pull request its branch names (ADR 0005), and that run is `main`'s: the queue's commit is the one `main` moves to, so `check.yml` does not run again on `main` after a merge, a release or deploy pull request's check, and a deploy's in the queue, reads the queue's run on the commit it is made on, and the README's badge shows the queue's latest run, which may be of a pull request the queue turned away rather than of `main`; the title check reads the title from the pull request the queue's branch names (one expression for that branch, in `review-gate.ts`, which a test holds `pr-title.yml` to); the app's gates compare the group's commit with its base, `main` with the pull requests ahead of it in the queue, so each is judged on its own change, and skip `tests first`, which is not required and which the line reads from the pull request.
- **The app's gates run a change's code on `merge_group` no more privileged than on `pull_request`.** They refuse every other event. A pull request reaches the queue only once the `review` check has passed, so the queue's commit is `main` with changes Martin opened or approved at their heads, which `main` will hold a moment later. Their token is read-only, as their workflow sets it, which a caller cannot widen, and they are passed no secret.
- **A caller moves its pin and its triggers together.** `review.yml` judges only a `workflow_run`, so a repository that calls it at a pinned commit runs a `review-requested.yml` of its own, as this one does, and its `review.yml` on `workflow_run` after it. The app's repository pins a commit from before the gate left `pull_request_target`, with that commit's triggers, and moves to the new shape in one change.
- **A caller passes the App's key by name.** `review.yml` declares `REVIEW_APP_PRIVATE_KEY` as an optional secret of `workflow_call`. GitHub's documentation says a called job with `environment:` uses the caller's environment of that name, but a secret resolves to empty unless the caller passes it, by name, which works for a secret held only in the environment, or with `secrets: inherit`. Unpassed, the gate says its verdict and posts nothing.

### How the gate routes

- **Risk tags from the diff, never from labels** (`scripts/review-routing.ts`): `dependency-change` for a lockfile or package manifest anywhere; `security-headers` for the app's `src/headers.ts`, or a line of the app's code added or removed anywhere that names a security header or `SECURITY_HEADERS`; `test-loosening` for each test that test integrity excused as one the pull request's spec contradicts, read from the warning it annotates each with on its own check run; `code-owned` for a path CODEOWNERS on `main` gives Martin, read from `main` and never from the pull request; `release` for release-please's branch, or a change to its files alone; and `improvement` for a change to the app's typed list of flag names, `src/flag-names.ts`, or a line of the app's code, added or removed, that names the flag context's `flag` or calls an `.on(` (taking an ask away gives what it guarded to everyone). The last is broad on purpose: a line it catches that asks no flag holds a pull request for Martin, and one it missed would pass new behaviour unattended. A diff GitHub cannot list whole is tagged `code-owned`, and a file of the app's code GitHub gives no patch of, `improvement`.
- **The rule, the first that holds:** `martin-opened`, `martin-approved-head`, `exact-pin`, `low-risk`, `lights-out`, or `held`. A risk label (a tag's name, or `out-of-scope`) that anyone but Martin removed, by the pull request's issue events, holds it from every rule after his. In this repository, any pull request of the App's but an exact pin is held, whatever `AUTONOMY` says: the App merges nothing here but pins.
- **Test integrity fails closed.** `low-risk` and `lights-out` need the latest `gates / test integrity` check run GitHub Actions posted for the pull request's head, completed and successful, and a pull request into `main` that changes nothing under `.github/`, whose run is then the workflow `main` has. A missing, pending, skipped, cancelled or failed run, or one whose annotations GitHub gives fewer of than it counts, is no reading, and holds the pull request, saying which. A run of that name another App posted is never read; while any run GitHub Actions posted for the head is unfinished, a re-run queued among them, the latest completed is not the reading. A warning on a file that the gate cannot read as an excused test counts as one, so a change in test integrity's words holds rather than passes.
- **An exact pin's signatures are checked by cosign, against GHCR,** as `scripts/admission-ready.sh` checks them: the commit an image's `org.opencontainers.image.revision` label names is only a claim until cosign verifies a keyless signature by that repository's `build.yml` on `refs/heads/main` at that commit (`--certificate-github-workflow-sha`). The commit of each new pin must be `ahead` of the old one's by the compare API. The build's signatures are cosign's, kept beside the images, so GitHub's attestations API has none to read. Only the factory's and the app's images, under `the-roganator`, can be pinned so.
- **Lights-out is the caller's `AUTONOMY` variable.** `review.yml` reads `vars.AUTONOMY`, which GitHub resolves to the caller's repository's variables (or its `review` environment's) in a called workflow, and passes it to the gate. It is never an input, so the caller's own file cannot say it, and only an admin can set a variable; neither the factory's App nor any worker's credential may write one. The line, which reads the level from the store, enqueues only by a rule the level allows, so the stricter of the two wins.
- **The summary carries the verdict the line reads** (`policy/review-verdict.ts`): a block in an HTML comment with the rule, the tags with what gave each, and the head each pull request was judged at, beside the words Needs you shows. A hold that waits only for test integrity is marked `pending` (at most 300 characters): GitHub Actions' run of it is missing for the head, or one of its runs for the head has not completed, and no tag the level would not pass was found, which would hold it for those tags. The gate judges again when the gates finish, so the line can wait for it rather than take the hold for a refusal. Every other hold, a read of GitHub that failed among them, is not pending. In the merge queue each pull request in the stack is judged afresh at its head as it is now, never by a verdict judged for another commit.
- **It judges again when the gates finish.** A caller lists its gates' workflow beside `review requested` in its `workflow_run`, so a pull request held while test integrity runs is judged again once it has; `review-requested.yml` runs on a label's removal too.

### The order of the move

1. Before the transfer: the gate, its triggers, and an admission policy that admits images under either owner, signed by `build.yml` on `main` of the repository under either, through one attestor per owner, as Kyverno supports only one identity in each (ADR 0010). The gate runs, and posts nothing until its App is set up; nothing requires it. The app's repository gets the same, calling this repository's `review.yml` at a pinned commit, as it calls the title check.
2. Martin makes the review App in the organisation (App ID `5470762`, Client ID `Iv23liFNqAvApddT27zU`), able to write checks and read pull requests, with no webhook, installed on every repository there; transfers both repositories; gives each a `review` environment that only `main` may use, holding the App's key as `REVIEW_APP_PRIVATE_KEY`; and installs the factory's App on the organisation.
3. After the transfer, in a pull request of its own: the repositories' names wherever they are written, the settings (`scripts/github-settings.ts`: the queue, `review` required from the review App, no up-to-date rule, `main: review` gone), Kyverno's refusals taken again under the new policy, and the line's and the `implement` skill's ways of keeping a branch up to date, which the queue makes needless.
4. Once nothing runs an image built before the move, only `the-roganator`'s images are admitted, pinned or accepted: the admission policy, the deploy pull requests' checks, the factory's watches and `make admission-ready` name no other owner, and Kyverno's refusals are taken again under that policy.

The transfer happens before the app's next pull request opens, or after that pull request's pin has synced, never between: its pin and the journeys image its canary analysis runs would be caught between two signer identities.

## Why

Every merge makes every other open pull request out of date, and the up-to-date rule makes each run its gates again: merging *n* pull requests one after another runs them up to *n*(*n*+1)/2 times, browser tests and image builds included. The merge queue tests each pull request once, on `main` as it will be, and is offered only to repositories an organisation owns.

The queue cannot sit beside GitHub's review rule here. A pull request enters the queue only once every rule is met, and a bypassed rule is not met. Tried on 25 October 2026, in a throwaway repository in the organisation with this repository's two rulesets and the queue: with the queue in `main`, Martin's own pull request, unreviewed, was refused entry ("New changes require approval from someone other than the last pusher"), and a merge with `--admin` was refused because changes must go through the queue; with the queue in `main: review`, entry was refused the same way, and `--admin` merged around the queue. So review has to be something the queue can wait for: a check.

- **A check posted by an App of its own,** rather than by the factory's App or by a plain Actions job. The factory's App opens the pull requests the gate holds, so it must never post the verdict that lets them merge. A job's check is GitHub Actions', and any pull request that changes a workflow can add a job of the same name; requiring the check from one App's integration means only the holder of its key can post it.
- **Martin opened it, or approved its head,** because Martin is the only reviewer: every pull request that is not his waits for him, the App's, Dependabot's and anyone's, as `main: review` made them, and his own merge, as the bypass let them, with the checks still required.
- **By id, not login.** A login can be renamed, and the name then taken by someone else; an account's id never changes.
- **An organisation on the Free plan,** because the queue needs no paid plan for a public repository, and a move costs only names: GitHub redirects the repositories' URLs. It does not redirect GHCR's image names or the identity cosign certifies, which carry the owner, so images built before the move keep the old owner's name until newer builds replace them, and only then does admission trust the new owner alone.

## Consequences

- OpenSSF Scorecard's Branch-Protection check reads GitHub's review settings, not a check, so its score falls from 8 to about 3 to 5: it wants an approval rule on the branch. Code-Review is 0 already, since nobody else reviews. Martin will not keep a rule only he can bypass to keep a score.
- GitHub no longer holds code owners' review: Martin is the only code owner, and the gate holds every pull request he did not open for his approval, but the factory's App's exact pins and, in the app's repository, its untagged ones (and at Lights-out its tagged ones that are neither a release nor an improvement), none of which may touch a path CODEOWNERS names but a pin's.
- A pull request Martin opened passes whoever pushes to it after him, as the bypass did. Only Martin, Dependabot and the factory's App push branches here, and the other two only to branches they opened.
- Until the App is set up, the gate says its verdict in its run and posts nothing. Until the settings change, it is required by nothing.
- The line does not read `review` as one of a pull request's gates. The gate alone merges nothing: a pull request merges only once Martin or the line adds it to the queue ([approval routing](../../COMPONENTS/APPROVAL-ROUTING.md)), and a fault in the line cannot merge a change the gate holds.
- A pull request held for Martin, the App's included, shows a failing `review` until he approves its head: the check is the hold.
- The `review` environment is the only place the review App's key is kept. Its branch rule, `main` only, is set by hand before the key is added, and is what keeps a pull request into another branch from using it.
- In the queue, every pull request runs every check but the factory's App's deploy, which runs there as on its pull request: a release's browser tests and image builds run there too. That is one full run for each merge but a deploy's, in place of one for each pull request still open.
- `main` has no run of `check.yml` but the queue's. A commit that reached `main` some other way would go untested after it landed; the ruleset lets nobody push to `main`, and a release or deploy made on such a commit fails its check for want of the queue's run. A run reads only its own branch's caches and `main`'s, so `toolchain-cache.yml` keeps `main`'s cache of the toolchain each of `check.yml`'s jobs installs, which no run of `check.yml` on `main` now saves, and of each set the other workflows install; only a run on `main` saves one.
- A pull request with no `review` check waits, as one with a failing check does: the queue takes it only once every required check has passed. GitHub holds two kinds of run for a maintainer's approval before it reads a job, so no condition in a workflow can stop them. A review by Copilot that leaves comments, which GitHub treats as an outside contributor's, holds its run of `review-requested.yml`, and the run of `review.yml` that one starts on `main`'s head when its pull request closes; only Martin's reviews count, so neither has anything to judge. Each would leave a red cross, and a re-run keeps Copilot as the actor, so the gate's run it starts is held in turn: `copilot-held-runs.yml` deletes both every half hour, with the workflow's own token, which may write Actions and read the contents, and nothing else. It deletes only runs of those two workflows that Copilot's account started, held or failed with no job. A pull request from a first-time contributor's fork holds its runs of `review-requested.yml`, and may hold the gate's runs they start, so it has no check until Martin approves them, and his approval reaches the gate once he approves that review's runs, or re-runs the gate's last run for the pull request, which reads his reviews afresh.
- GitHub gives a run Dependabot starts no Actions secrets, and its documentation disagrees on whether a `workflow_run` after one counts as Dependabot's. If it does, the gate posts nothing when Dependabot opens or pushes, and its pull request has no check until Martin's review, whose run is his.
- An open pull request at the same commit as another holds that commit's check until it passes too: anyone can open one at the head of Martin's, from a fork, and it fails his check until he closes it or approves it. That is the price of one verdict per commit, which a check on a commit allows no other way; nothing reaches `main` through it, as the queue's commit is judged on the pull requests it carries, down to the one into `main`.
- GitHub runs no `pull_request` workflow on a pull request with a merge conflict, so it has no check until a push resolves the conflict and asks the gate.
- This decision supersedes ADR 0009: its two rulesets, its admin bypass, and the App's keeping its pull requests up to date before anyone approved them are gone.
