# 0017: The GitHub worker queues this repository's local deploy pins and pin moves once the gate passes them

## Decision

The factory's own deploy pull request for the local profile (`chore(deploy): run … on the local cluster`, labelled `deploy: local`, opened and moved by the deploy watch on `deploy/local`, ADR 0005) is added to the merge queue by the GitHub worker itself, as the App, with nobody's hand on it. It is added only when all of these hold, and once for each head (`github/deploy-queue.ts`):

- its head is the very commit the deploy watch wrote to `deploy/local` (`WatchedHeads`), or one a worker started since found already to be exactly the commit it would write (`github/own-commit.ts`: one commit of the App's on `main`, writing each pin file as the watch would and nothing else), so a restart costs the pull request nothing: a branch at any other commit, moved by anyone by any route, is not the watch's work, is not added, and the watch writes its own commit again on its next pass;
- the App opened it, from this repository's `deploy/local` into `main`, not a draft, with the label and a title the deploy watch writes; and it is the deploy watch's as the watch left it, as the worker's door refuses any worker that asks to write `deploy/local` or its scratch branch, open a pull request from either, give a `deploy:` label, or act on a pull request from either;
- the review App's own `review` check on that head passed it as `exact-pin` (ADR 0014): every changed line a digest under `deploy/`, each image signed by `build.yml` on `main`, from a commit ahead of the pin it replaces;
- every other check `main`'s rulesets require has a latest run on that head that finished and did not fail, by anyone but the factory's App;
- GitHub says it does not conflict with `main`, and it is not queued already.

The pin watch's pull request for the scan's moves at a set of files (ADR 0013), which the gate passed as `move` or `major` (ADR 0022), is added on the same terms, each open one on its own, when all of these hold:

- its head is the very commit the pin watch wrote to its branch, or one a worker started since found already to be exactly that commit, by the same reading as the deploy pin's: the pin edits the watch makes on `main`'s head through the pin guard, or the files the scan's pin step made, committed whole, and nothing else; any other commit is not added, and the watch writes its own again on its next pass;
- the App opened it, from this repository's `factory/pin/<files>` (one segment, the pin watch's branch) into `main`, not a draft, labelled `pin`, and the App alone ever gave it that label or took it off, by its events, so Martin holds one by taking the label off, though the pin watch puts it back; and no earlier unmerged pull request of the App's from the same branch, back to the last one merged from it, had its label taken off by anyone else, so his hold outlasts the watch closing it and opening it again, at any target, until a pull request from the branch merges after he took the label off;
- the pin watch is told to take moves (`PIN_WATCH_ONLY`), and commits only those: a head it did not write, one left open from an earlier setting among them, fails the first condition;
- the review App's own `review` check on that head passed it as `move` or `major`: no other rule, so not a hold, and not Martin's approval of a held one (`martin-approved-head`), which leaves adding it his;
- the autonomy level and auto-merge Martin set, read from the store just before the enqueue, queue that rule (`enqueues`, `policy/line.ts`): a `move` at Guarded and Lights-out, a `major` at Lights-out alone, nothing with auto-merge off, and nothing when the worker cannot read them (ADR 0022);
- every other required check, and the conflict and the queue, as for the deploy pin.

It goes in at the head the gate judged (`expectedHeadOid`), through the same action and guards the line's enqueue uses. A failure that may pass is tried again on the next pass, a few times; a refusal is kept and signed as the worker keeps its others. In a dry run the watches write nothing to GitHub, so no head there is one they wrote, and the queues add and record nothing; a dry run's own deploy pull request, which GitHub never had, merges on the dry run's own clock (`dry-run-reads.ts`).

Nothing else is queued this way: not the app's deploy pull request, which stays the line's within Martin's autonomy level and auto-merge; not a pull request the gate held, even once Martin approved its head; not a release, an improvement, a pull request of any other profile, or anything that is not the App's.

## Why

- **The merge Martin made was the change.** An image is built and signed from a commit of `main` that Martin, or the line within what he set, already merged. The local deploy pin only says that the local cluster should run it: once the gate has passed it as an exact pin and its checks are green, merging it decides nothing, and a hand on it only adds a wait before the cluster runs what `main` already holds.
- **The gate is the review.** `exact-pin` passes only digests of images `build.yml` signed on `main`, each moving forward; the gate reads the diff, GHCR and Sigstore itself, and the merge queue runs the required checks again on its own commit. The worker adds nothing the gate did not pass at that head, and GitHub merges nothing the queue's checks do not pass. The worker cannot widen what merges: it only saves the click.
- **A move is made, not trusted.** The gate passes `move` only when the pull request is, byte for byte, the scan's moves as the gate makes them itself on `main` (ADR 0022). The worker's terms read the branch, the label and who gave it, not because the gate needs them but so that nothing but the pin watch's own pull request is queued on the rule: the gate trusts no branch name, and passes the scan's moves from any branch here, so the same commit on another `factory/` branch would pass it, and is still not queued: the worker's door refuses every worker that asks to add a pull request to this repository's merge queue, and to write or act on the branches and pull requests the two watches own, so only the watches add to it, and only what they made and left. A pull request the gate held is a decision, and Martin's approval of it makes it his, not the worker's, to add.
- **The local profile alone.** The local cluster is Martin's development cluster, and disposable. A profile that serves visitors would deploy to them, and its pins stay a decision until an ADR says otherwise.
- **The worker, not the line.** The line acts on work items, and the factory's own deploys carry none: the line does not watch them (`line/deploy.ts`). The worker already opens and moves the pull request, knows the label and the branch, and holds the only key that can enqueue. A watch beside the deploy watch keeps the whole deploy in one place, and works while the line is stopped.
- **Not GitHub's auto-merge.** Auto-merge, turned on for a pull request, queues whichever head next meets the rules, and the worker would have to turn it on again for each build. Adding a judged head to the queue names the head, as the line's enqueue does.

## Consequences

- An image built on `main` reaches the local cluster without Martin: the deploy watch opens the pin, the gate passes it, the worker queues it, the queue merges it, and Argo CD syncs it.
- A move the scan found reaches `main` without Martin, at the level he set: the pin watch opens it, the gate makes it again and compares, the worker queues it, the queue merges it. One the gate holds, or the level does, waits for him, with its reason.
- The worker's log says why a deploy or pin pull request waits, once for each head and reason (`the deploy pull request waits to be queued`, `the pin pull request waits to be queued`), and that it queued it (`added the deploy pull request to the merge queue`, `added the pin pull request to the merge queue`).
- The queue taking it out because a check failed on its commit is not the end of a head: `main`'s checks can fail for a reason that is not the change's, and a pin that waits a day for a flake is a day unpatched. The worker adds the head again on its next pass, three times in all (`QUEUE_TRIES`), counting the failures from GitHub's record of the pull request, so a restart does not start the count again. A change that breaks `main` fails every time: after the third the worker stops, and says so in a comment on the pull request, with the checks that failed last. That head is then Martin's.
- A required check that fails on the head itself, a job that hangs and is cancelled by its time limit among them, is not the end of a head either: once the gate passed it, the watch writes the same commit again with a `Checks-run:` line, so GitHub runs every check on a new head, three runs in all (`RUN_TRIES`, read from the head's own message), then says so in a comment and leaves the head to Martin. The App starts no run itself: its Actions permission stays read.
- The queue taking it out any other way (Martin took it out, GitHub found a conflict) leaves that head for Martin, as the line leaves its own. A worker that restarts may add the same head once more, and the queue tests it again.
- A branch protection or permission change that stops the App enqueueing is kept, signed and logged as a `token-permission` refusal (`refusals.ts`), and the head waits for Martin.
- `AGENTS.md`'s rule on who merges names the worker beside Martin and the line.
