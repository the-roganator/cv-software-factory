# 0019: The review gate passes a pin move it can prove from the pull request, and holds every other for Martin

## Decision

In this repository the factory's App merges nothing but pins. Beside the exact pin of an image of ours (ADR 0014), the review gate passes, as `pin-move`, a pull request of the App's into `main`, from the start and never retargeted, whose head no other pull request has had (a check run is the head's, whichever base it ran for), that moves one pin of the vulnerability scan's list (ADR 0013) forward, when it can prove each of these from the pull request itself, and holds it for Martin, with the first reason it could not, otherwise (`scripts/pin-move.ts`):

1. **Pins only.** Every file it changes was there before, regular, with its mode, and changes line for line, each line only in a version or a digest; nothing under `.github/`, and neither of mise's files. The change is what the merge makes: the head merged onto `main`'s tip, against that tip, never against a merge base `main` has left. The list worked out on both has the same items at the same places, and differs in one move's pins alone: one image, one chart or one value of a chart, from one pin to one other. Every line it changes is one of them, each line its old text with the pin's own span alone replaced, and the list reads every pin at the head (`--unlisted`).
2. **Not what judges.** Trivy's, Syft's and Kyverno's own pins are Martin's: what judges a move cannot vouch for its own replacement, and Kyverno, admission itself, is what tells the platform check that every image policy enforces.
3. **Signed where its publisher signs.** An image of ours passes only as an exact pin, signed by `build.yml` on `main`. A third-party image is held to its digest alone, as admission admits it (ADR 0010): the next condition's.
4. **Forward on its line.** The gate resolves the target itself, with the function the scan resolves a fix with (`newestOf`): the same tag at its index digest now, or the newest tag on its line at its index digest now, never a major and never back; a chart's later release (never a prerelease) on the same major, in its repository's index.
5. **No record goes stale.** Each refusal record's policy hash, computed at the base and at the head with `scripts/policy-hash.ts` as `main` has it, is the same.
6. **Nothing else that runs changes.** For a chart, a value, or an image in `deploy/`, the manifests rendered at the base and at the head differ only in the moved image's references and the chart's own version labels (`helm.sh/chart` and `app.kubernetes.io/version`, by those keys alone).
7. **The scans show it.** The pinned Trivy, on a fresh database, on the image as it was and as it would be, on each platform we run (`linux/amd64`, CI's, and `linux/arm64`, the local cluster's), each apart: a finding with a fix is gone, and nothing is new at High or above. A finding is its advisory and its package, never the path it was found at. An index without one of the platforms, or a scan that read nothing, proves nothing.
8. **Something ran it.** GitHub Actions' latest run at the head of the job that runs what the pin runs succeeded, rather than being skipped, and was made by the workflow that has that job: its check suite's run is of this repository's file, on the pull request, from a branch here, at that head, so a job of the same name in any other workflow proves nothing. `ZAP scan` for ZAP's image, `image builds` for a Dockerfile's stage outside `deploy/`, each shard of `tests` for Postgres, whose pin CI's own database is: `scripts/check-kind.sh` gives each of those the kind `code`, which runs every check. What a cluster runs from the change (a chart, a value, a third-party image in `deploy/`, Postgres among them) needs `platform` (`platform.yml`), which made a cluster from the change and passed only once every Application was Synced and Healthy, every image policy enforced and every pod ran, and a workload there to start it: some Deployment, StatefulSet or DaemonSet of the head's rendering that names the moved image, not a hook and not scaled to nothing, since an image only a hook or a Job runs is never pulled by that cluster; `check-kind.sh platform` says `cluster` for any change to `deploy/`, and a `platform` it skipped made none, and holds. Argo CD's chart is installed by `make up`, not by a merge, and is held; k3s waits for Martin whatever `platform` says, since his cluster moves with it, and a refusal record it stales (`mark-refusals.json`, Traefik's, which k3s brings) is the one `platform` took at the move's head, committed from that run's `refusal-records` artifact, never an edited one.

The gate trusts nothing the pull request says of itself: not its title, label, description or branch. The move is worked out from its two commits, and the code that works it out (the list, the policy hash, the Trivy pin) is `main`'s. Its head is data: its lines are read as text before anything renders it, so only a change of versions and digests on the base's own lines reaches kustomize, Helm or Trivy. A fact the gate could not read (a registry that did not answer, a scan that read nothing, a check skipped, a page cut short) is no proof, and holds.

`review.yml` works the move out in a job of its own, `pin move` (`scripts/pin-moves.ts`), with read-only permissions (`actions: read` among them, for which workflow made each check run) and no secret, from `main`'s whole checkout and its locked dependencies, and hands the gate one answer for each pull request it would judge, by number and head. The gate, which holds the review App's key, reads no head itself: it takes an answer only for the App's pull request here that is no exact pin, at the head it judges, and holds one it has no answer for. The gate runs again when `check.yml` or `platform.yml` finishes, as a pin move waits for the job that runs its pin.

Nothing is queued on the rule yet: a pull request it passes is Martin's to add to the merge queue, as before.

## Why

- **A patch that waits is unsafe too.** The scan gives a High seven days and a Critical two (ADR 0013), and most of what it finds is fixed by a pin moving on its own line. Martin's review of a digest is the weakest control on the list: he cannot judge one by eye. What he would want to know is whether it is the publisher's current image on the same line, whether it fixes something and brings nothing worse, and whether it runs; the gate can read each of those itself, and a reading is better evidence than a glance.
- **Prove, do not trust.** Every condition is a positive proof, so a fact unread is a hold, never a pass. The rule reads its target from the registries and the charts' indexes, its findings from its own Trivy, and its runs from GitHub Actions' check runs at the head, never from the pull request, the scan's artifact or anything the App wrote: a compromised App, or a pull request shaped to look like its pins, must still get past the registry, the scan and a job that ran it.
- **One pin, one move.** A move is the unit the scan names and the App opens (`moves.json`): one pin's name, from one value to one other. A second pin, a line that is not a pin, a pin the list does not read, or any other change holds the whole pull request, so nothing rides in beside a pin.
- **The key never meets the head.** The review App's token can post the check every ruleset requires. Rendering and scanning the head beside it would give any flaw in kustomize, Helm, yq or Trivy that token; in a job of its own, with none, such a flaw can at most give a wrong answer for the App's own pull requests here, which the rest of the gate still bounds.
- **What judges stays Martin's; what a cluster runs is proved by one.** A scanner moved by the rule would judge its own replacement. A chart or a value runs nowhere but a cluster, so it passes only on `platform`, which made one from the change itself, with no secret, and everything on it ran. k3s is the cluster itself: a merge does not move Martin's, so its move is his whatever a cluster in CI showed.

## Consequences

- ADR 0014's rule gains `pin-move`, after `exact-pin`, in this repository alone; the app's line moves the app's pins. Spec 4.3's check passes a pin move beside the deploy pin, and no other change of the factory's to a path CODEOWNERS gives Martin. `policy/review-verdict.ts`'s `RULES`, and the events' `GATE_RULES`, name it.
- **The risk it accepts: a pin merges into the factory with nobody watching.** A third-party publisher's compromised rebuild of the same tag would pass if it scans clean, fixes something and passes the job that runs it. A third-party image has no signature of ours; what stands between it and `main` is the exact digest the tag names, the same line, the scans on both platforms, and a check that ran it. What ran it is `linux/amd64`'s image alone, as every runner is amd64: the `linux/arm64` image the local cluster runs is scanned, never started, before it merges. `platform` shows a chart's images start and become ready on a cluster with no secret; it does not show what they would do with the local cluster's. Martin's approval of a digest would not have stopped it either.
- A pin a publisher signs is held to its digest alone until the gate names that publisher's signer; naming one is a change to this rule.
- Every verdict here waits for the `pin move` job: its setup, about a minute, when it has nothing to work out, and a few minutes more for the App's pull requests, whose two commits it fetches, renders and scans. In the app's repository the job does not run.
- `scripts/pin-moves.ts --print --as-app <owner/name> <number>` replays a past pull request as the App's, with no say of Martin's: what the rules would have said of the same change.
