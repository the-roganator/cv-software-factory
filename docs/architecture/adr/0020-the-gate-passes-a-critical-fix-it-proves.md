# 0020: The review gate passes a Critical vulnerability's fix it can prove from the pull request, and holds every other update for Martin

## Decision

In the app's repository, beside the exact pin and the untagged change (ADR 0014), the review gate passes, as `critical-fix`, a pull request of the factory's App's into `main`, from a branch in the repository, from the start and never retargeted, whose head no other pull request has had and whose branch no other comes from, that carries a dependency's change, when it can prove each of these from its two commits, and holds it for Martin with its `dependency-change` tag and the first reason it could not, otherwise (`scripts/critical-fix.ts`):

1. **Pins only.** The change is what the merge makes, the head merged onto `main`'s tip, against that tip. Every file it changes is one of the app's pins, modified in place, regular, with its mode: `pnpm-lock.yaml` and `package.json`; a `FROM` line's tag and digest, in the same image repository; `mise.toml`'s Node, with its entry in `mise.lock` (its version, checksums and nodejs.org's download URLs for that version), both together, forward on its major. Nothing under `.github/`, no other lockfile, nor `pnpm-workspace.yaml`, `.npmrc`, a `.pnpmfile.cjs` or `patches/`: none of them is a pin. **The lockfile is the gate's own.** The gate works out the move: a package its pinned Trivy rates Critical in the base's lockfile, with a fix, and the version the head gives it, from `package.json`'s range where that moves and from the lockfile's keys where it does not. Only those two words cross from the head, and each is checked: a version the registry publishes, forward of the version found, at or above every Critical's fix, never across a major the fix does not need. A head that moves no such package, or two, holds. The gate then runs the pin step's own derivation for that move on a checkout of the base: the same code (`writePins`, `apps/runner/src/pins.ts`, imported), the same pnpm (the version this repository's `mise.lock` holds, which the runner image installs, found from the gate's own checkout, never the app's `packageManager`), `--lockfile-only --ignore-scripts --ignore-pnpmfile`, over the base's `package.json` and `pnpm-workspace.yaml`, the base's `.npmrc` moved aside and the registry given on the command line, as the pin step does, with no secret in its environment. The head passes only if its `pnpm-lock.yaml` and `package.json` are, byte for byte, what that wrote. Anything else holds: `the lockfile is not the one this move writes`.
2. **Forward on its line.** Each `FROM` it moves is the same tag at its index digest now, or the newest tag on its line at its index digest now, never a major and never back: a pin move's own check (`imageForward`, ADR 0019).
3. **The scans show the fix.** The gate's pinned Trivy, on a database refused when older than a day, on the lockfile at both sides and on each moved image at both sides on `linux/amd64` and `linux/arm64`, and Node's own database on the Node mise pins at both sides, as the daily scan reads Node (Trivy reads no Node runtime): a finding the scanner rates Critical at the base, with a fix, is gone at the head, and its package is still listed at or above the advisory's fixed version. Each version is ordered in the format Trivy says its target is in (the result's class and type, never the look of the string): npm's semver for a lockfile's packages and Node, dpkg's for Debian's and Ubuntu's packages, apk's for Alpine's (`scripts/critical-fix-versions.ts`). Any other format, or a version that does not parse in its own, holds, naming the format. Every package the base's scan lists is in the head's, and where an image names its Node at the base it names one at the head. Fixes in two packages are a group, and held. A report that does not parse, reads nothing, or gives a finding with no package or advisory, holds.
4. **Nothing new.** No scan of the head finds an advisory, in a package, at High or above that the base's did not, nor one it gives no rating (Critical, High, Medium or Low) the gate reads.
5. **Only what the fix needs moves.** For a package's fix: the package fixed is the move's, everything else the lockfile moves is what pnpm moved for it (condition 1), and no image or Node moves. For Node's: mise's pin and every `FROM`, and every image whose Node the scan reads runs the Node mise pins; nothing in the lockfile. For an image's own package: one image repository's `FROM` lines, its Node unchanged.
6. **Every gate passes.** GitHub Actions' latest run at the head of each of the app's required checks but `review` succeeded, each made by the workflow that has its job, for this pull request: `lint, types, tests`, `image builds`, the title, and the five gates. The app's ruleset is read when the fix is: a check it requires that the gate does not know, or a ruleset that does not require `review`, holds. The runs at the head ran on the pull request's merge with `main` as `main` was then; the merge queue runs the same checks again on its own commit. `test/node-pins.test.ts` holds mise's Node to each `FROM`, and `image builds` runs the runtime image's `node --version` against mise's, so the runtime's Node, which its distroless tag does not name, is the Node scanned.

The gate trusts nothing the pull request says of itself: not its title, label, branch, description, nor an advisory's words; and no figure another job wrote, the gates' own counts among them. The fix is read from the gate's own scans of the two commits, by `main`'s code. The proof is computed from data, never from a build: the head's app image exists nowhere, and the gate runs no code of a pull request's. "The base's image" in the plan is read as what the image is made of that a dependency's move can change: the lockfile it installs from, and the `FROM` images, whose Node the runtime is.

`review.yml` works the fix out in a job of its own, `critical fix` (`scripts/critical-fixes.ts`), in the app's repository alone, with read-only permissions (`actions: read` among them, to tell which workflow made each check run) and no secret, from `main`'s whole checkout, and hands the gate one answer for each pull request it would judge, by number and head. The gate takes an answer only for the App's pull request there, at the head it judges, that carries a dependency's change and is no exact pin, and holds one with no answer. The tags the rule passes are `dependency-change` and `code-owned` on the pins' own files that CODEOWNERS gives Martin (`Dockerfile`, `mise.toml`, `mise.lock`) and nothing else: a test loosened, a header, an improvement, a release, any other path of his, or a diff GitHub did not list whole, holds it. It passes whatever `AUTONOMY` says, as `low-risk` does: the gate reads one value, `lights-out`, and Guarded is the store's level, which the line alone reads. The line adds it to the merge queue at Guarded and Lights-out with auto-merge on (`ENQUEUES`, `policy/line.ts`), never at Supervised, and tells Martin of each such merge (`app-fix-merged`).

## Why

- **A Critical is due in two days (ADR 0013), and Martin is a person.** A fix that waits for him at night is the exposure the deadline is there to end. What he would check is what the gate can read for itself: that the finding is gone by the scanner's word, that nothing worse came, that nothing else moved, and that every gate passed.
- **The publisher's rating holds, never releases.** A package's publisher is the party whose code would merge, so a "Critical" it gives its own advisory could carry its release past Martin. The gate reads the pinned scanner's rating alone. Node is the one exception, and the only one: Trivy reads no Node runtime, so the scan has no other source for Node than Node's own security database, which is its publisher's. A Node fix that database rates Critical passes alone (Martin, 14 November 2026); without it, every Node fix would wait, and Node's are the fixes that most need to be quick. No other publisher's rating ever releases a change.
- **A finding that disappears is not a fix.** A package removed, renamed, aliased or sourced elsewhere, an image swapped, or a scan that read less, all make a finding go. Every package the base lists must still be listed, from the registry, at or above its fix.
- **The lockfile is one the gate wrote.** pnpm and Trivy each read a lockfile's text their own way: pnpm installs a frozen lockfile's snapshots as written, by keys and merge keys a rule reading YAML does not see, and Trivy takes a package's version from a field pnpm ignores. Every rule that listed what a head's lockfile may hold left another gap. Byte equality with what the pin step's derivation writes from the base closes the class: nothing the head writes is read except as text pnpm would itself have written, so Trivy scans a lockfile no hand shaped. What runs is pnpm's resolver, a third party at the version `main` pins, on the base with one name and one version from the head, with no script, no pnpmfile and no secret, as the pin step runs it.
- **One dependency, one move.** A move is the unit the scan names and the line takes. A second package, an unrelated bump, a range of another package or a group holds, so nothing rides in with a fix.
- **The key never meets the head,** as for a pin move: the job that scans has no secret, and a flaw in Trivy can at most give a wrong answer for the App's own pull requests there.

## Consequences

- ADR 0014's rule gains `critical-fix`, after `pin-move`, in the app's repository alone. Its sentences that the App passes there only untagged, or at Lights-out, and that Guarded merges only low-risk, exact pins and Martin's approval, no longer hold: a Critical fix passes tagged at every level, its pins in Martin's paths among it, and the line queues it at Guarded. `RULES` (`policy/review-verdict.ts`), `GATE_RULES` and the console's words name it.
- **The risk it accepts: a fix that is itself malicious.** A publisher who ships a real fix for a real Critical, with something else in the same release, passes if the scanner sees nothing new at High. What bounds it, from what the app's settings hold: the Dockerfile installs with `--ignore-scripts` and `pnpm-workspace.yaml` allows no install script (it allows builds of none, and sets no age rule of its own: pnpm's default holds a release younger than a day); the canary's analysis rolls back a release whose journeys or errors go bad; and Martin is told of each such merge. Nothing here reads what the new code does.
- **What a build could hold that the scans do not:** the image is built by `build.yml` on `main` after the merge, from the lockfile and the `FROM` images the gate scanned, plus the app's own source, which the rule holds unchanged. What the scans cannot see is what installing does beyond the lockfile's packages (no scripts run), and the runtime's Node, which its tag does not name: that one is proved by `image builds` running it at the head. A finding in a file the build writes itself is the daily scan's to find after the merge.
- **The queue's commit** is judged today as any is: the gate judges the pull request at its head afresh, taking the job's answer for that head, and the merge queue requires the app's checks of its own commit, which holds the change on `main` as it will merge. This rule changes none of that. The runs it reads at the head are the head's own workflows, which the change cannot alter, since `.github/` holds; a head whose branch is older than `main` ran the merge base's.
- Every verdict in the app waits for the `critical fix` job: its setup, about a minute, and a minute or two more for each of the App's dependency changes, whose two commits it fetches and scans, and a few seconds for a package's move, whose base it fetches once more for pnpm to write the lockfile on. The app's caller grants `actions: read`, and lists `check` beside its gates in its `workflow_run`, so the gate judges again once `image builds` and the tests finish.
- `scripts/critical-fixes.ts --print --as-app <owner/name> <number>` replays a pull request as the App's, with no say of Martin's, Trivy through Docker. A replay of a merged pull request judges its image's tag as it is now, so a move the publisher has since gone past is held.
- Lights-out still passes a dependency's change by its tags, as it always has: this rule adds a pass at every level, and takes none away.
- **The cost of a derived lockfile: drift.** The derivation depends on when it runs. A release published between the pin step's run and the gate's, of the package moved or of one pnpm resolves for its new version, makes the two lockfiles differ once it is past pnpm's release age (the app sets none, so pnpm 12's default holds: a day), and so does a `main` that moved its lockfile under the branch. Each is a hold with the derivation's words, never a bypass: the change waits for Martin, and the line's next pin step writes it again. Equality is never loosened to cure it.
- **An image's OS packages** are ordered by dpkg's and apk's own rules, which the gate implements itself: no dependency the repository has orders them. A move of `mcr.microsoft.com/devcontainers/base` from `3.0.12-noble` to `3.0.13-noble`, whose 25 Critical findings with a fix are all `linux-libc-dev` at `6.8.0-147.147`, fixed at `6.8.0-149.149`, is ordered by dpkg; the rule is the app's alone, so in this repository such a move is a pin move's to prove, and in the app the same shape of move would pass if its scans showed every one gone and nothing new at High.
- A Node fix whose new images also clear an operating system package's Critical is two packages fixed, a group, and held.
